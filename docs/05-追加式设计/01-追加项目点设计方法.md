# 追加项目点设计方法

## 目的

追加式设计用于控制 WorkPilot 的演进。任何新增连接器、Memory 类型、Verifier、工具、公共模型或基础设施能力，都必须先证明它符合产品定位，并明确对现有闭环的影响。

## 哪些变更必须建立设计记录

- 新增公共模块或跨模块接口；
- 修改核心领域模型；
- 新增数据源、工具或外部写操作；
- 引入数据库、队列、缓存或新模型供应商；
- 修改状态机、重试、预算和失败策略；
- 修改 Memory 写入、读取或过期规则；
- 修改评测指标或 Golden 数据结构；
- 影响权限、隐私、审计或高可用的变更。

普通 Bug 修复、测试补充和不改变行为的重构可直接开发，但仍应更新相关实现细节。

## 设计流程

### 1. 定义问题

说明真实业务问题、用户场景和当前实现为什么不足。不能以“想使用某项技术”代替问题定义。

### 2. 检查产品边界

回答：

- 是否服务企业项目协作主场景；
- 是否有更小、更确定性的解决方法；
- 是否引入无关领域或不可控权限；
- 是否能够通过评测证明价值。

### 3. 分析现有系统影响

列出受影响模块、接口、数据、状态、Trace、测试和文档，特别关注向后兼容和迁移。

### 4. 比较方案

至少包含“不实施”或“保持现状”方案，并比较复杂度、可靠性、成本、安全和可测性。

### 5. 定义最小实施范围

把能力拆成可单独验收的最小闭环，明确本次不做什么，避免一次设计承担全部未来需求。

### 6. 定义验收证据

必须在开发前确定：

- 自动化测试；
- 评测指标；
- 运行产物；
- 失败行为；
- 性能或成本约束；
- 文档更新项。

### 7. 分阶段实施

推荐顺序：领域模型与接口 → 确定性实现 → 测试 → 主链路接入 → 评测 → 文档与状态更新。

## 设计记录状态

- `草案`：正在讨论，不能作为实现依据；
- `已接受`：边界、方案和验收明确，可以进入开发；
- `实施中`：代码正在开发；
- `已完成`：验收通过并同步文档；
- `已替代`：被新设计取代，保留历史原因；
- `已拒绝`：明确不实施并记录原因。

## 完成要求

设计记录不能只描述理想架构。实现完成后必须回填实际差异、测试、指标、遗留问题和后续项目点。
