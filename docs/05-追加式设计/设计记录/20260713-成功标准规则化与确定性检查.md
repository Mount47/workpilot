# 成功标准规则化与确定性检查

## 基本信息

- 日期：2026-07-13
- 状态：设计已确认，开发中
- 关联模块：Plan、ToolSpec、ToolRegistry、PlanValidator、PlanExecutor、Runtime、Trace

## 背景

PlanStep.success_criteria 当前是自然语言。它能够表达业务意图，但不能被程序稳定执行，也不能把模型生成的任意文字直接当成可信规则。

如果仅凭 Handler 没有抛出异常就把步骤标记为 completed，会遗漏“工具调用成功但输出结构不满足契约”的情况；如果让 LLM 自己声明规则并执行，又会扩大模型权限并造成不可重复判断。

## 目标

1. 保留自然语言 success_criteria 作为人类可读说明；
2. 新增系统控制的 success_rule_ids；
3. ToolSpec 声明该工具必须执行的规则；
4. PlanDraft 不暴露 success_rule_ids，模型不能修改；
5. PlanValidator 检查步骤规则与 ToolSpec 完全一致；
6. ToolRegistry 在 Handler 返回后执行确定性规则；
7. 规则失败时 PlanStep fail closed；
8. 规则结果进入 plan.json、Working Memory 和 Trace；
9. 不把业务验证失败错误地解释为工具执行失败。

## 双轨成功标准

### 自然语言标准

字段：`success_criteria`

用途：

- 解释该步骤为什么存在；
- 约束 Planner 的业务描述；
- 供报告、评测和人工审计阅读。

它不直接执行，也不决定步骤状态。

### 确定性规则

字段：`success_rule_ids`

用途：

- 指向系统注册的稳定规则；
- 根据 ToolResult.status 和 output_summary 检查输出契约；
- 产生结构化 RuleCheck；
- 决定工具执行是否真正满足步骤契约。

规则 ID 由 ToolSpec 和系统代码赋值，不允许模型生成。

## 权限边界

- PlanStepDraft 不增加 success_rule_ids；
- ConstrainedLLMPlanner 根据已注册 ToolSpec 补入规则 ID；
- DeterministicPlanner 使用同一组系统规则 ID；
- ToolSpec 引用未知规则时拒绝注册；
- PlanStep 的规则集合与 ToolSpec 不一致时，PlanValidator 拒绝计划；
- Runtime 不接受 LLM 自定义 Python 表达式、JSONPath 或任意代码规则。

## 第一版规则

所有工具都必须执行：

```text
tool_result.completed
```

核心工具再执行输出摘要结构规则：

```text
workspace.scan.summary_valid
evidence.extract.summary_valid
claims.build.summary_valid
artifacts.render.required_outputs_present
verification.run.summary_valid
artifacts.finalize.persisted
```

规则只读取安全字段：status、output_summary 和 evidence_ids，不读取或记录完整业务 output。

## 业务验证边界

verification.run 的 `error_count > 0` 不代表工具执行失败。该工具的确定性规则只检查：

- check_count 和 error_count 是非负整数；
- error_count 不大于 check_count；
- Handler 正常返回 ToolResult。

是否修订由 Runtime 的业务验证门决定。这样可以区分：

```text
工具执行失败
  -> PlanStep failed

工具执行成功，但报告验证未通过
  -> PlanStep completed
  -> Runtime 请求定向修订
```

## 数据结构

```text
SuccessRuleCheck
  rule_id
  passed
  message

SuccessCriteriaEvaluation
  passed
  checks[]
```

PlanStep 保存最近一次 attempt 的 success_evaluation。重入时清空旧结果，执行后写入新结果；历史 attempt 由 Trace 保留。

## 执行顺序

```text
validate Plan rule IDs
  -> invoke ToolHandler
  -> validate ToolResult type
  -> evaluate registered success rules
  -> passed: PlanStep completed
  -> failed: PlanStep failed + SuccessCriteriaError
```

## Trace

`tool_call_completed` 和 `plan_step_completed` 增加安全的 success_evaluation。

规则失败时，`tool_call_failed` 和 `plan_step_failed` 记录：

- error_type=success_criteria_failed；
- 失败 rule_id；
- 不含 ToolResult.output 的规则消息。

## 分阶段实施

### 第一阶段：规则协议

- SuccessRuleCheck；
- SuccessCriteriaEvaluation；
- SuccessRuleRegistry；
- 默认规则注册；
- success_rule_ids 系统字段。

### 第二阶段：执行接入

- ToolSpec 注册时检查规则；
- PlanValidator 检查规则集合；
- Executor 执行规则并 fail closed；
- Runtime Trace 和 Working Memory 同步。

### 第三阶段：扩展准备

- 为连接器增加 Schema 规则；
- 为错误类型建立修订动作映射；
- 评测规则误报、漏报和执行开销；
- 持久化每次 attempt 的规则结果。

## 非目标

- 不执行模型生成的任意规则；
- 不用 LLM 判定工具是否成功；
- 不在本阶段实现复杂业务 KPI 规则引擎；
- 不把 Claim/Citation Verifier 合并进通用 Tool Rule；
- 不读取完整 ToolResult.output 做可观测规则。

## 验收标准

- 默认六步计划的规则全部通过；
- LLM 计划自动使用 ToolSpec 规则，模型无法覆盖；
- 未知规则和规则不匹配在执行前拒绝；
- ToolResult 摘要不合法时步骤 failed，后继 blocked；
- 业务验证 error 仍触发修订而非工具失败；
- 重入只保留当前规则结果，Trace 保留 attempt；
- 完整测试、业务 Stub Eval 和 Planner Eval 保持通过。

## 当前限制

- 第一版规则主要验证执行状态和安全摘要结构；
- 自然语言业务语义仍由 Verifier 和离线评测负责；
- 规则结果尚未持久化到数据库；
- 尚无面向企业自定义规则的受控 DSL。
