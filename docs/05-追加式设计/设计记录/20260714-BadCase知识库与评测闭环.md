## 问题与动机

普通工程问题文档混合了假设风险与真实故障，无法清晰回答“项目实际踩过什么坑、如何定位、如何防回归”。同时，Evidence Gate 已实现，但 Eval Runner 没有读取门禁 Trace，无法量化修复收益和成本。

## 用户场景

开发者在真实模型运行后发现报告遗漏来源，需要登记原始事实、关联修复、生成回归样本，并在以后面试或版本回归时快速复盘。

## 产品边界判断

Bad Case 文档保存脱敏事实和证据摘要，不充当线上日志仓库；Eval Runner 只统计安全 Trace 字段，不读取或复制业务正文。

## 当前实现

- 新增 Bad Case 总览、规范和模板；
- BC-001 登记首次 qwen-plus 来源遗漏；
- EvalCaseResult 和 EvaluationSummary 增加覆盖、接受、丢弃和修复成本指标；
- EvalCase 通过 `bad_case_ids` 关联真实异常；
- CLI 展示关键证据质量指标；
- 修复成本限定在 Evidence Repair 事件窗口。

## 目标与非目标

### 目标

- 真实异常可编号、可追踪、可回归；
- Run passed 但业务不完整也能登记；
- 修复代码、测试、指标和真实复跑形成闭环；
- 未知模型价格不伪造成本。

### 非目标

- 不自动上传业务日志；
- 不使用模型自动判定所有 Bad Case；
- 本阶段不建设完整线上告警平台。

## 最终决策及原因

文档负责案例事实与复盘，Eval Runner 负责可重复指标，Trace 作为两者的共同依据。案例只有复跑原始场景后才能标记为“已回归验证”。

## 安全、权限和隐私

禁止保存 API Key、完整敏感 Prompt 和企业原文；优先记录 event_type、计数、错误类型、Artifact 名称和脱敏摘要。

## 测试与评测

新增 Repair 窗口统计、未知价格 null、Bad Case ID、Optional Metric 和宏平均测试，并扩展 Stub Eval 断言。当前 144 个测试通过。

## 验收标准

- BC-001 可从总览定位；
- Eval JSON 包含新增指标；
- CLI 可见关键覆盖指标；
- 后续模型调用不被误算为 Repair 成本；
- 未知价格输出 null；
- 真实复跑前案例状态保持“修复中”。
