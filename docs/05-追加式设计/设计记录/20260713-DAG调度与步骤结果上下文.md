# DAG 调度与步骤结果上下文

## 基本信息

- 日期：2026-07-13
- 状态：设计已确认，开发中
- 关联模块：Plan、PlanExecutor、Tool Registry、Runtime、Trace

## 背景

当前 Planner 已能生成并校验结构化计划，Runtime 的六个核心步骤也已经统一通过 Tool Registry 和 ToolHandler 执行。但是，Runtime 仍在代码中按固定顺序调用步骤，PlanStep.dependencies 只用于执行前检查，尚未真正驱动调度。

同时，各工具的内部结果仍通过 Runtime 局部变量传递。该方式适合固定流水线，但无法支撑动态步骤、独立分支、失败传播、运行恢复和步骤级观测。

## 目标

1. 由 PlanStep.dependencies 决定可执行顺序；
2. 第一版采用确定性串行拓扑调度，保持行为可复现；
3. 增加 blocked 和 skipped 状态，区分执行失败、依赖阻塞与主动跳过；
4. 一个分支失败时，阻塞其后继步骤，但允许无依赖关系的分支继续；
5. 检测无可执行步骤但仍有 pending 步骤的调度死锁；
6. 用 StepResultStore 保存同一次 Run 内的 ToolResult；
7. Trace 能解释步骤为何就绪、为何阻塞以及调度最终状态；
8. 保留当前验证失败后的受控重入能力。

## 职责边界

### PlanValidator

负责静态合法性：

- 步骤 ID 唯一；
- 依赖存在；
- 不存在循环依赖；
- 工具已注册；
- 输入符合工具 Schema；
- 当前 Runtime 兼容策略满足安全约束。

### SerialDAGScheduler

负责运行时状态推进：

- 查找依赖均 completed 的 pending 步骤；
- 按 Plan 中的稳定顺序串行执行；
- 捕获步骤失败并传播 blocked；
- 保存安全的步骤执行结果；
- 检测调度死锁；
- 返回结构化调度结果，不决定具体业务修订策略。

### PlanExecutor

负责单步骤执行安全：

- 校验工具仍然存在；
- 校验依赖状态；
- 控制 reentrant；
- 更新 running、completed、failed、attempts 和 last_error_type；
- 通过 Registry 调用 Handler。

### Runtime

负责业务编排：

- 创建和验证计划；
- 绑定当前 Run 的工具 Handler；
- 驱动 Scheduler；
- 根据验证错误决定是否进入修订；
- 生成 Artifact、Trace 和最终 RunResult。

调度器不理解 Claim、Evidence、Artifact 或验证错误的业务含义。

## 状态模型

```text
pending
  ├── running ── completed
  │       └───── failed
  ├── blocked
  └── skipped
```

- `failed`：该步骤确实开始执行，但工具或 Handler 失败；
- `blocked`：该步骤未执行，原因是至少一个依赖 failed、blocked 或 skipped；
- `skipped`：系统根据显式策略主动不执行该步骤；
- `completed`：工具调用成功完成；
- 验证不通过属于业务结果，不自动等同于工具执行失败。

## 确定性调度规则

1. 每轮先传播依赖终态，再查找 ready 步骤；
2. ready 条件是自身为 pending，且全部依赖为 completed；
3. 多个步骤同时 ready 时，严格按 Plan.steps 中的顺序执行；
4. 某步骤失败后，不执行依赖它的后继步骤；
5. 与失败步骤无依赖关系的分支继续执行；
6. 若不存在 ready 步骤、也没有新的状态传播，但仍存在 pending，则报告死锁；
7. 第一版不并发执行，后续只有在评测证明有收益时才增加受控并发。

## StepResultStore

StepResultStore 是当前 Run 内的临时步骤结果上下文：

```text
step_id -> ToolResult
```

规则：

- 只允许保存已执行步骤的 ToolResult；
- 同一步骤正常情况下只能写入一次；
- 受控重入时允许覆盖，并保留 attempt 维度的 Trace；
- ToolResult.output 只在进程内传递，不进入 Trace；
- Trace 和持久化只使用 output_summary、evidence_ids、status 等安全字段；
- 后续 Runtime Handler 应通过依赖步骤 ID 读取上游结果，不再依赖外部局部变量。

## 成功标准策略

当前 PlanStep.success_criteria 是自然语言描述，不能直接声称已经由程序确定性验证。第一版采用分层策略：

1. 工具执行层：以 Handler 是否成功返回 ToolResult 判定执行完成；
2. 结构校验层：由 Pydantic 输出模型验证类型、必填字段和范围；
3. 业务验证层：由 verification.run 检查 Claim、Citation 和 Artifact；
4. 后续将 success_criteria 改造成稳定规则 ID，再由规则注册表执行确定性检查。

在规则 ID 落地前，Trace 必须区分“工具已完成”和“业务标准已验证”，禁止把自然语言 success_criteria 自动标为通过。

## 修订与重入

验证步骤成功执行但返回业务错误时，Runtime 可以暂停最终化并发起定向修订：

```text
claims.build -> artifacts.render -> verification.run
```

- 只有 ToolSpec.reentrant=true 的步骤允许重入；
- 每次重入增加 attempts；
- StepResultStore 用新结果覆盖当前值；
- Trace 保留每个 attempt 的工具调用与错误摘要；
- finalize 只能在 Runtime 接受验证结果后执行。

## Trace 事件

在现有 plan_step 和 tool_call 事件之外，调度器补充：

- `scheduler_started`；
- `scheduler_step_ready`；
- `scheduler_step_blocked`；
- `scheduler_deadlocked`；
- `scheduler_completed`。

事件只记录 step_id、依赖状态、结果摘要和计数，不记录 ToolResult.output。

## 分阶段实施

### 第一阶段：调度内核

- PlanStepStatus 增加 blocked、skipped；
- StepResultStore；
- SerialDAGScheduler；
- 稳定拓扑顺序；
- 失败传播和死锁检测；
- 单元测试。

### 第二阶段：Runtime 接入

- RuntimeExecutionContext；
- Handler 从 StepResultStore 读取依赖输出；
- Scheduler 驱动初始计划；
- 验证后暂停、重入和继续最终化；
- 调度事件进入 Trace。

### 第三阶段：恢复与并发准备

- StepResult 持久化；
- 幂等键；
- 从 checkpoint 恢复；
- 按工具副作用和资源配额决定是否允许并发。

## 非目标

- 本阶段不实现并行执行；
- 不允许模型绕过 PlanValidator 动态插入任意工具；
- 不把自然语言成功标准伪装成确定性规则；
- 不在 Scheduler 内实现报告修订业务；
- 不在 StepResultStore 中持久化敏感完整输出。

## 验收标准

- 菱形 DAG 按稳定拓扑顺序执行；
- 一个分支失败后，其后继为 blocked，独立分支仍可完成；
- pending 步骤无法推进时能稳定报告死锁；
- ToolResult 可供下游步骤读取，Trace 不泄露内部 output；
- Runtime 现有主链路与最多三轮修订语义保持不变；
- 完整单元测试、业务 Stub Eval 和 Planner Eval 均通过。

## 当前限制

- 当前 RuntimePlanPolicy 仍只接受六个核心步骤；
- success_criteria 仍为自然语言；
- StepResultStore 只存在于单进程内；
- 跳过策略、取消语义、超时和 checkpoint 尚未实现。
