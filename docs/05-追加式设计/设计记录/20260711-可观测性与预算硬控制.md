## 问题与动机

当前 Provider 主要返回字符串或 Pydantic 对象，模型、Token、延迟、请求 ID 和停止原因在模块边界处丢失。Mission Contract 虽然声明最大步骤、时间和 Token 预算，但 Runtime 没有强制执行。动态 Planner 和 Memory 如果建立在该基础上，会产生不可审计、不可限制的执行状态。

## 用户场景

一次 Run 结束后，开发者应能回答：执行了哪些步骤、调用了哪些模型、每次调用消耗多少 Token 和时间、为什么重试或失败、是否触发预算限制。用户设置较小预算时，Runtime 必须确定性终止并输出失败原因与预算快照。

## 产品边界判断

该能力属于 Agent 后端的基础可靠性建设，不改变企业项目协作业务范围，不增加外部写权限，是 Planner、Memory、恢复和高可用的前置条件。

## 当前实现

- TraceJournal 只保存 sequence、event_type、data 和 timestamp；
- Provider 文本调用返回字符串，结构化调用只返回模型对象；
- EvidenceExtractor 和 ClaimBuilder 不向 Runtime 暴露模型调用元数据；
- max_steps、time_budget_seconds、token_budget 未被 Runtime 消耗；
- CLI 尚未传递 token_budget。

## 目标与非目标

### 目标

- 定义统一 GenerationResult、StructuredGenerationResult 和 EvidenceExtractionResult；
- 捕获 Provider、模型、Token、延迟、请求 ID、停止原因和错误类型；
- EvidenceExtractor 与 ClaimBuilder 向 Runtime 暴露全部模型调用；
- 实现 ExecutionBudget，强制步骤、时间和 Token 预算；
- Trace 增加 event_id、step_id、parent_step_id；
- 记录 step_started、step_completed、model_call_completed 和 budget_summary；
- 预算耗尽时 fail closed，并保留 Trace；
- 增加自动化测试。

### 非目标

- 本阶段不实现厂商价格表和精确成本计算，只保留 estimated_cost；
- 不实现分布式 Trace 后端；
- 不实现 Tool Registry；
- 不实现后台任务取消和跨进程恢复；
- 不保存完整 Prompt 和敏感模型输出。

## 备选方案

### 方案一：Provider 内部直接写 Trace

接入简单，但 Provider 与 Runtime Trace 强耦合，难以独立测试，也无法统一预算控制。

### 方案二：Provider 返回结构化调用结果，由 Runtime 记录和计量

接口变更较多，但调用元数据拥有清晰的数据流，Runtime 可以统一执行预算和 Trace。

### 保持现状

无法准确评估成本、定位模型错误，也不能安全引入动态 Planner。

## 最终决策及原因

采用方案二。Provider 只负责返回调用事实；EvidenceExtractor 和 ClaimBuilder 聚合调用结果；Runtime 是预算与 Trace 的唯一控制者。

## 模块与依赖影响

- `providers/base.py` 新增调用结果模型并改变接口返回值；
- OpenAI、Claude 和 Stub Provider 同步适配；
- EvidenceExtractor 和 ClaimBuilder 保存本轮模型调用；

## 数据和接口变更

GenerationResult 至少包含：

```text
content
provider
model
input_tokens
output_tokens
latency_ms
request_id
finish_reason
estimated_cost
```

StructuredGenerationResult 包含已校验 value 和该次操作发生的所有 GenerationResult；EvidenceExtractionResult 包含 candidates、调用列表和可选 error_type。

## 安全、权限和隐私

Trace 默认不保存完整 Prompt、原始响应和 API Key。请求 ID、模型名和 Token 可记录；内容只记录数量、Hash 或摘要。

## 失败、重试与恢复

- Provider 重试的每次调用都必须计入 Token 和 Trace；
- 模型调用发生后才发现 Token 超预算时，记录调用后立即失败，不进入下一步骤；
- 步骤和时间预算在步骤开始前检查；
- 预算异常使用稳定错误类型并由 Runtime 转为 failed；
- finally 始终写出 budget_summary 和 trace.json。

## 可观测性

目标 Trace 层级：

```text
Run
├── planning
├── retrieve.workspace
├── retrieve.evidence
│   └── model_call_completed × N
├── synthesize.claims
│   └── model_call_completed
├── synthesize.artifacts
└── verify
```

- 全量测试和最小评测通过；
- 文档状态与代码一致。

- OpenAI-compatible、Claude 和 Stub Provider 已统一返回可观测结果；

## 遗留问题与后续项目点

- estimated_cost 字段已经保留，但尚未引入版本化价格表；
- 当前没有 Tool Registry，因此 Workspace 操作以步骤事件记录，尚无统一 tool_call 协议；
- Provider 内部一次结构化操作的有限重试会在操作返回后统一计量，不能在同一操作的重试中途停止；
- Trace 尚未实现字段级脱敏、Hash 和输出大小限制；
- Run 与 Trace 尚未持久化到数据库；
- 下一阶段应建立 Working Memory，把计划、步骤、证据、验证反馈和预算状态统一到 RunContext。
