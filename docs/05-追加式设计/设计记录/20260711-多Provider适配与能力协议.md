# 追加项目点设计记录：多 Provider 适配与能力协议

## 元信息

- 状态：已完成
- 创建日期：2026-07-11
- 最后更新：2026-07-11
- 关联模块：Provider、Registry、Settings、Trace、Evaluation
- 关联问题：Provider 分支硬编码；缺少 Gemini；无法声明厂商能力差异

## 问题与动机

WorkPilot 已支持 Stub、Claude 原生 Messages API，以及 OpenAI、DeepSeek、Qwen/百炼和 GLM 的 OpenAI-compatible 接口，但 Registry 仍以条件分支和零散常量描述厂商。系统无法查询 Provider 的传输协议、结构化输出、Usage、原生工具和多模态能力，也无法通过统一入口接入 Gemini 或企业自建 OpenAI-compatible Gateway。

“支持多模型”不能只意味着修改 base_url。Provider 必须在统一调用结果、结构化输出校验、Token 统计、错误语义和测试契约上保持一致，同时允许保留厂商原生能力边界。

## 官方依据

- OpenAI Structured Outputs 支持 JSON Schema 和 Python Pydantic，并建议优先于只保证合法 JSON 的 JSON Mode：<https://developers.openai.com/api/docs/guides/structured-outputs>；
- Google 官方提供 Gemini 的 OpenAI compatibility，并说明统一 OpenAI Schema 是平台快速接入路径：<https://ai.google.dev/gemini-api/docs/openai>；
- Google 同时建议需要 Gemini 高级原生能力时使用 `google-genai`，兼容层不与原生能力一一对应：<https://ai.google.dev/gemini-api/docs/partner-integration>；
- Gemini Structured Outputs 支持 JSON Schema/Pydantic，但只支持 JSON Schema 子集：<https://ai.google.dev/gemini-api/docs/structured-output>。

## 用户场景

用户可以通过相同 CLI 和 Runtime 切换 GPT、Claude、DeepSeek、GLM、Qwen、Gemini 或企业自建兼容端点。Runtime 继续获得统一 GenerationResult、Token、延迟和错误类型，不需要了解具体 SDK。

## 产品边界判断

多 Provider 是企业应用降低厂商锁定、支持私有网关和进行模型评测的基础能力。它不改变项目分析业务模型，也不能绕过统一 Evidence、Claim、Plan 和预算边界。

## 当前实现

- Claude 使用 Anthropic 原生 SDK；
- GPT、DeepSeek、Qwen/百炼和 GLM 使用 OpenAI-compatible Adapter；
- Registry 通过名称条件分支返回 Provider；
- Gemini 与自定义兼容端点未注册；
- Provider 没有公开能力描述；
- API 异常尚未归一为稳定错误类型。

## 目标与非目标

### 目标

- 定义 ProviderTransport、ProviderCapabilities 和 ProviderDescriptor；
- 使用数据驱动 Registry 管理所有内置 Provider；
- 保持 Claude 原生 Adapter；
- 注册 GPT、DeepSeek、Qwen、百炼、GLM 和 Gemini 的 OpenAI-compatible Adapter；
- 增加 `custom` Provider，支持任意 OpenAI-compatible 企业网关；
- Settings 增加 Gemini 和 Custom API Key；
- 统一认证、限流、超时、网络、服务端和未知错误分类；
- 增加 Registry、Gemini、Custom 和错误契约测试；
- 文档明确兼容层与原生能力差异。

### 非目标

- 不在本阶段实现 Gemini File、Search、Code Execution 等原生工具；
- 不把所有厂商特有参数强行塞入统一接口；
- 不维护实时模型价格和完整模型目录；
- 不更改现有 OpenAI 默认模型或做模型升级；
- 不声称一个 Adapter 覆盖厂商全部 API 能力。

## 备选方案

### 方案一：所有厂商都走 OpenAI-compatible

代码最少，但 Claude 和 Gemini 的原生能力、错误和 Usage 可能无法正确表达，兼容层也不是一一映射。

### 方案二：统一核心协议，按传输协议复用 Adapter，必要时保留原生 Adapter

核心文本、结构化结果和 Usage 复用；Claude 保持原生；Gemini 当前核心能力先走官方兼容层，未来高级能力增加原生 Adapter。

### 方案三：每个厂商完全独立实现

能够使用全部原生能力，但重复代码、行为漂移和测试成本过高。

## 最终决策及原因

采用方案二。WorkPilot 的当前核心需求是文本生成、结构化 Claim/Plan、Evidence 抽取和 Usage。Gemini 官方兼容层足够覆盖该核心边界；需要 Gemini 高级原生工具时，再增加单独的 `gemini-native` Adapter，而不是污染通用接口。

## 模块与依赖影响

- 新增 `providers/specs.py` 和 `providers/errors.py`；
- Registry 改为由 ProviderDescriptor 驱动；
- Settings 和 `.env.example` 增加 Gemini/Custom；
- OpenAI-compatible 与 Claude Adapter 包装 SDK 错误；
- Provider Trace 继续使用 descriptor name 作为 provider 字段；
- 测试覆盖所有注册名称和关键配置。

## 数据和接口变更

内置 Provider：

```text
stub
openai
claude
deepseek
qwen
bailian
glm
gemini
custom
```

Custom 必须显式传入 model 和 base_url，避免系统猜测企业网关。

## 安全、权限和隐私

- API Key 只从 Settings 或显式参数进入 SDK，不写 Trace；
- Custom base_url 和 model 必须显式配置；
- Provider 切换不改变 Workspace、Tool 和 Memory 权限；
- 错误 Trace 记录稳定分类，不默认记录 SDK 原始响应正文。

## 失败、重试与恢复

统一错误类型：authentication、rate_limit、timeout、network、server、invalid_response、unknown。Timeout、Network、Rate Limit 和 Server 默认可重试；Authentication 和 Invalid Response 不进行无界重试。

## 可观测性

GenerationResult 继续记录真实 provider name、model、Token、延迟、请求 ID 和停止原因。ProviderCallError 提供稳定 error_type 和 retryable，供后续 Retry Policy 与 Metrics 使用。

## 实施阶段

1. Provider 描述和能力模型；
2. 数据驱动 Registry；
3. Gemini 与 Custom；
4. 错误归一化；
5. 配置、测试和文档。

## 测试与评测

- 所有名称可查询 Descriptor；
- Claude 使用 native transport；
- GPT、DeepSeek、Qwen、百炼、GLM、Gemini 使用兼容 transport；
- Gemini 默认 URL、模型和 API Key 映射；
- Custom 缺少 model/base_url 时明确失败；
- SDK 401、429、timeout、connection 和 5xx 分类；
- Stub Smoke 和 Eval 回归。

## 验收标准

- Gemini 和 Custom 可通过 Registry 构建；
- 现有 Provider 行为不回退；
- Runtime 不新增厂商条件分支；
- Provider 能力可以被代码和文档查询；
- 错误类型稳定且经过测试；
- 全量测试和最小评测通过。

## 实际实施结果

- 新增 ProviderTransport、ProviderCapabilities 和 ProviderDescriptor；
- Registry 已改为由 Descriptor 数据驱动，Runtime 无厂商条件分支；
- 注册 stub、openai、claude、deepseek、qwen、bailian、glm、gemini 和 custom；
- Claude 保持原生 Anthropic transport；Gemini 使用 Google 官方 OpenAI compatibility 覆盖当前文本与结构化核心能力；
- Custom 必须显式提供 model 与 base_url，可接企业私有 OpenAI-compatible Gateway；
- Settings 与 `.env.example` 已增加 GEMINI_API_KEY 和 CUSTOM_API_KEY；
- 新增 ProviderErrorType、ProviderCallError 和 SDK 异常分类；
- Runtime、Plan 和 Working Memory 使用稳定 Provider 错误类型，不记录 SDK 原始响应正文；
- 新增 `workpilot providers` 命令展示 transport、默认模型和结构化模式；
- 新增 Registry、Gemini、Custom、错误分类、OpenAI 限流和 Claude 认证错误测试；
- 全量测试 71 passed，总体覆盖率约 88%；最小 Stub 评测继续通过。

## 遗留问题与后续项目点

- Gemini 当前只覆盖兼容层核心能力，File、Search、Code Execution 和原生 Interactions API 需要单独 `gemini-native` Adapter；
- OpenAI 当前仍使用跨厂商 Chat Completions 兼容边界，尚未增加独立 Responses API Adapter；
- Structured Output 当前统一为 Prompt + Pydantic 校验重试，没有按 Descriptor 启用厂商原生 schema 参数；
- Qwen、GLM、DeepSeek 和 Gemini 尚未执行带真实 API Key 的端到端质量评测；
- Provider 自动重试策略尚未基于 retryable 错误统一实现；
- 没有版本化模型目录、价格表和 Provider 健康检查；
- 新增其他兼容厂商优先通过 Custom 验证，出现原生能力需求后再建立专用 Descriptor/Adapter。
