# 追加项目点设计记录：结构化计划与确定性执行器

## 元信息

- 状态：已完成
- 创建日期：2026-07-11
- 最后更新：2026-07-11
- 关联模块：Planning、Tool Registry、Runtime、Working Memory、Mission Contract
- 关联问题：Planning 只有状态名；Runtime 主流程写死且没有可检查计划

## 问题与动机

当前 Runtime 会进入 planning 状态，但没有生成 Plan。扫描、抽取、Claim 构建、Artifact 渲染、验证和最终写入直接写在 `_run_pipeline()` 中，无法在执行前校验依赖、工具权限和最小步骤预算，也无法向 Working Memory 提供结构化计划状态。

直接增加 LLM Planner 会掩盖这些基础缺口：模型即使输出 JSON，Runtime 仍可能不按计划执行，或者计划引用不存在、未授权、循环依赖的工具。

## 用户场景

一次 Run 开始时，系统先生成一个结构化计划，验证每个工具存在且获准、依赖无环、步骤预算足够，再由 PlanExecutor 驱动实际 Runtime 操作。验证失败后的 Claim/Artifact/Verify 步骤可以受控重入并累计 attempt。

## 产品边界判断

结构化规划属于受控 Agent 的核心能力，继续由后端掌握执行权，不增加外部权限。确定性 Planner 是后续受限 LLM Planner 的可靠基线。

## 当前实现

- RunState 包含 planning；
- WorkingMemory 能保存步骤状态，但没有 Plan；
- Mission Contract 有 allowed_tools；
- WorkspaceTools 直接由 Runtime 调用；
- Revision Loop 由 Runtime 控制，最多三次。

## 目标与非目标

### 目标

- 定义 Plan、PlanStep、PlanStepStatus 和 ToolSpec；
- 定义受控 Tool Registry；
- 校验 ID、工具注册、Contract 白名单、依赖存在、依赖无环和最小步骤预算；
- 实现 DeterministicPlanner，生成当前可信主链路；
- 实现可重入 PlanExecutor，验证失败时允许受控重跑 Claim、Artifact 和 Verify 步骤；
- Runtime 的实际操作通过 PlanExecutor 触发；
- WorkingMemory 导出 Plan 状态；
- 输出 `plan.json`；
- 增加测试和 Trace 计划事件。

### 非目标

- 本阶段不实现 LLM Planner；
- 不允许模型创建新 Tool；
- 不实现并行 DAG 调度；
- 不实现分布式 Executor；
- 不实现任意参数绑定表达式；
- 不改变现有三次修订上限。

## 备选方案

### 方案一：只让模型生成计划文本

展示简单，但计划无法校验，也不控制真实执行，不具备工程意义。

### 方案二：结构化计划、注册工具和确定性执行器

前期改造较多，但能够证明计划与实际执行一致，并为 LLM Planner 提供安全边界。

### 保持现状

无法证明 Agent 的规划能力，也无法支持后续计划调整和恢复。

## 最终决策及原因

采用方案二，并先使用 DeterministicPlanner。Planner 只决定计划，PlanValidator 决定计划是否可执行，PlanExecutor 决定步骤生命周期，Runtime Handler 执行真实业务操作。

## 模块与依赖影响

- 新增 `planning/models.py`、`registry.py`、`validator.py`、`planner.py` 和 `executor.py`；
- Mission Contract 默认工具改为当前六个高层受控工具；
- Runtime 生成、验证并执行 Plan；
- WorkingMemory 保存 Plan 的安全状态摘要；
- Artifact 增加 `plan.json`；
- Trace 增加 `plan_created`、`plan_validated` 和计划步骤 attempt 信息。

## 数据和接口变更

默认工具：

```text
workspace.scan
evidence.extract
claims.build
artifacts.render
verification.run
artifacts.finalize
```

PlanStep 包含 ID、目标、工具、输入、依赖、期望输出、成功标准、是否需要 Evidence、状态、attempt 和最后错误类型。

## 安全、权限和隐私

- Plan 只能引用 Registry 中存在的工具；
- 每个 Tool 必须同时存在于 Contract allowed_tools；
- Plan Artifact 不保存 Prompt、业务正文或工具输出；
- Planner 无权执行工具；
- Executor 不允许未校验 Plan 执行。

## 失败、重试与恢复

- Plan 校验失败在任何业务工具执行前 fail closed；
- Step Handler 失败时 PlanStep 标记 failed；
- 已完成步骤可以由 Runtime 明确要求重入，attempt 累加；
- 依赖步骤必须至少成功完成一次；
- Revision 只允许重入 claims.build、artifacts.render 和 verification.run；
- Runtime 总步骤预算继续作为最终硬边界。

## 可观测性

Trace 记录 Plan 创建、验证和执行 attempt；WorkingMemory 回答当前 Plan 状态；plan.json 保存最终计划与每个步骤的真实执行次数。

## 测试与评测

- 重复 ID、未知工具、未授权工具、缺失依赖、循环依赖和预算不足；
- 默认计划通过；
- Executor 顺序、依赖、失败状态和受控重入；
- Runtime plan.json 与 RunContext；
- Stub Smoke 和 Eval 回归。

## 验收标准

- Runtime 的六个主要业务操作都由已验证 PlanStep 触发；
- Plan 校验在工具执行前完成；
- Plan 状态与真实执行 attempt 一致；
- 修订重入受到白名单限制；
- plan.json 和 run_context.json 可解释实际执行；
- 全量测试与最小评测通过。

## 实际实施结果

- 新增 Plan、PlanStep、PlanStepStatus 和 ToolSpec；
- 新增默认 Tool Registry，注册六个高层受控工具并声明 reentrant 与 evidence_required 属性；
- PlanValidator 已检查重复 ID、未知/未授权工具、缺失依赖、循环依赖和最低步骤预算；
- DeterministicPlanner 生成六步骤可信基线计划；
- PlanExecutor 已实际驱动 Runtime Handler，并维护状态、attempt 和最后错误类型；
- 只有 claims.build、artifacts.render 和 verification.run 允许受控重入；
- WorkingMemory 已导出不含业务输入的安全 Plan 摘要；
- 成功运行输出最终 `plan.json`，Trace 记录计划创建、验证和步骤执行；
- 新增一次验证失败后定向重入测试，确认扫描、抽取和最终写入各执行一次，Claim、Artifact、Verify 各执行两次；
- 全量测试 56 passed，总体覆盖率约 86%；最小 Stub 评测继续通过。

## 遗留问题与后续项目点

- 当前 Planner 为确定性基线，尚未根据用户目标改变步骤；
- Registry 目前保存 ToolSpec，实际 Handler 映射仍由 Runtime 提供；
- Executor 为显式顺序调用，不支持并行 DAG；
- success_criteria 目前是可审计描述，尚未自动判定；
- Plan 只在成功 Finalize 后单独写入 plan.json，提前失败时通过 run_context.json 查看；
- 下一阶段应实现受限 LLM Planner：只能从 Registry 选择工具，输出同一 Schema，并继续经过 PlanValidator；
- LLM Planner 必须与 DeterministicPlanner 在评测中对比后才能成为默认策略。
