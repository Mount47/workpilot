# 追加项目点设计记录：Claim 主链路与最小评测

## 元信息

- 状态：已完成
- 创建日期：2026-07-11
- 最后更新：2026-07-11
- 关联模块：Domain、Runtime、Synthesis、Verification、Evaluation、CLI
- 关联问题：引用真实但不支持结论；缺少效果基线

## 问题与动机

当前 Runtime 直接从 Evidence 生成 Markdown 和 JSON。Citation Verifier 只能证明引用指向真实原文，无法把报告结论作为独立对象验证，也无法计算 Claim Support Rate。没有统一 Claim 后，长期记忆还可能把未经验证的生成文本写成项目事实。

## 用户场景

用户要求系统根据项目资料生成报告。系统应先形成结构化 Claims，验证每条 Claim 的证据契约，再由通过验证的 Claims 渲染交付物。评测系统应能够用 Golden Evidence 和预期状态衡量当前基线。

## 产品边界判断

该能力直接服务于证据驱动企业项目分析，是 Memory、Planner 和持久化之前的必要可信边界，不引入新的外部权限或数据源。

## 当前实现

- 已有 SourceLocator、Evidence、Claim、ProjectSnapshot 基础模型；
- EvidenceExtractor 已输出正式 Evidence；
- Synthesizer 仍直接消费 Evidence；
- Citation Verifier 不验证 Claim；
- 没有 EvalCase、指标计算和 Eval CLI。

## 目标与非目标

### 目标

- 增加 ClaimCategory 和 ClaimBuilder；
- 建立 `Evidence → ProjectSnapshot/Claims → Artifacts` 主链路；
- 增加确定性 Claim-Support Verifier；
- 将 Claim 验证错误纳入现有有限修订循环；
- 输出 `project_snapshot.json`；
- 建立最小 EvalCase、Runner、指标与 CLI；
- 保持 Stub 路径确定性和全部现有测试通过。

### 非目标

- 本阶段不实现 LLM Judge 语义支持判断；
- 不实现长期 Memory；
- 不实现人工标注管理平台；
- 不实现完整 Precision/Recall 文本匹配；
- 不实现 Planner、数据库或企业连接器。

## 备选方案

### 方案一：生成报告后再反向抽取 Claim

优点是保留现有生成方式；缺点是同一事实经历两次模型转换，Claim 可能与报告不一致，验证链路复杂。

### 方案二：先生成结构化 Claim，再确定性渲染 Artifact

优点是 Claim 成为唯一业务结论来源，Markdown 与 JSON 不会绕过验证；缺点是第一版报告表达能力和风险字段较简单。

### 保持现状

无法衡量结论支持度，也不能安全建设长期记忆。

## 最终决策及原因

采用方案二。真实模型负责从 Evidence 生成结构化 Claim Draft，系统分配稳定 Claim ID 并构建 ProjectSnapshot；Stub 根据 Evidence 确定性生成 Claim。Synthesizer 只负责从 Snapshot 渲染 Artifact。

## 模块与依赖影响

- 新增 `analysis/claim_builder.py`；
- Domain 增加 ClaimCategory；
- Synthesizer 从 Snapshot 渲染，不再直接进行三次自由文本生成；
- Runtime 在每次生成/修订尝试中重建 Snapshot；
- Verification 增加 ClaimSupportVerifier；
- 新增 `evaluation` 包和 CLI 命令。

## 数据和接口变更

- Claim 新增 `category`；
- Runtime 新增 `project_snapshot.json` 输出；
- verification report 同时包含 Citation 和 Claim 检查；
- EvalCase 第一版保存 workspace、goal、expected_evidence_quotes 与 expected_status。

## 安全、权限和隐私

ClaimBuilder 只能看到当前 Contract 的 Evidence；引用不存在时由 Verifier 拒绝。Eval Runner 只运行显式配置的本地 workspace，不读取外部路径。

## 失败、重试与恢复

Claim 验证 error 与 Citation error 使用同一有界修订循环。达到最大次数仍失败则 fail closed。Eval 单案例失败不终止整个评测集，而是记录失败结果。

## 可观测性

Trace 增加 `claims_built` 事件和 Claim 验证计数。完整 Token 和成本追踪仍属于下一阶段。

## 实施阶段

1. Domain 与 ClaimBuilder；
2. Snapshot 驱动的 Synthesizer；
3. ClaimSupportVerifier 与 Runtime；
4. Evaluation 模型、Runner 和 CLI；
5. 测试、文档和状态同步。

## 测试与评测

- ClaimBuilder Stub 与模拟真实 Provider；
- ClaimSupportVerifier 的有效、缺失引用、原文不一致、unknown 和 derived 场景；
- Runtime Smoke 输出 Snapshot；
- Eval 指标计算和多案例不中断；
- 全量回归测试。

## 验收标准

- Artifact 由 ProjectSnapshot Claims 确定性生成；
- Runtime 同时执行 Citation 和 Claim 验证；
- `workpilot eval` 可输出机器可读报告；
- 现有测试与新增测试全部通过；
- 状态和实现文档与代码一致。

## 实际实施结果

- 新增 ClaimCategory 和 ClaimBuilder；
- Provider Candidate、正式 Evidence、Claim、ProjectSnapshot 已形成连续主链路；
- Synthesizer 改为从 ProjectSnapshot 确定性渲染全部 Artifact；
- Runtime 同时运行 ClaimSupportVerifier 与 CitationVerifier；
- 输出 `project_snapshot.json` 和带分类检查的 verification report；
- 新增 Evaluation 模型、Runner、`workpilot eval` 和最小 Stub 基线；
- 最小基线实际运行：任务完成、Evidence Precision/Recall、Citation Validity、Claim Support 均为 100%，Unsupported Claim 为 0%；该结果仅证明单个确定性 Stub 案例闭环，不代表真实模型质量；
- 全量测试 41 passed，总体覆盖率约 77%。

## 遗留问题与后续项目点

- Analytical Judgement 目前明确标记为 semantic verification pending；
- 第一版 Golden Suite 只有一个确定性案例，需扩充为人工标注的多场景集合；
- 风险、行动项、里程碑仍需更完整的领域结构；
- Provider 尚未返回 Token、延迟、成本和标准错误；
- 下一项目点应是完整 Trace 与 Runtime 预算硬控制。
