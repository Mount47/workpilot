# 总体架构

## 架构目标

WorkPilot 本质上是一个由后端系统承载的 Agent。模型负责语言理解、受限规划和内容生成；后端负责数据访问、控制流、状态、记忆、验证、权限、预算和可观测性。

## 目标架构

```text
CLI / API / Web
        │
        ▼
任务接入与 Mission Contract
        │
        ▼
Agent Runtime ─────────────── Trace / Metrics / Audit
        │
        ├── Planner
        ├── Plan Executor
        ├── Budget & Policy Guard
        └── Recovery Controller
        │
        ▼
工具与连接器层
        ├── Workspace 文档
        ├── Excel / CSV
        ├── PDF / Word
        ├── 会议与邮件
        └── 任务管理系统
        │
        ▼
标准化来源与 Evidence Store
        │
        ├── 项目状态分析
        ├── Memory Manager
        └── Claim Builder
        │
        ▼
报告生成 → 引用验证 → 结论支持验证 → 定向修订
        │
        ▼
Artifacts / Project Snapshot / Verification Report
        │
        ▼
持久化存储与评测系统
```

## 分层职责

### 接入层

负责接收任务、参数和身份信息，返回运行状态和交付物。接入层不直接执行模型或数据工具。

### Runtime 控制层

负责运行状态机、计划校验、步骤调度、预算检查、失败处理和最终状态。任何模型计划都必须经过 Runtime 校验后才能执行。

### 工具与连接器层

负责受控读取外部数据，并转换为统一来源结构。连接器不得直接生成最终业务结论。

### 证据与项目分析层

负责证据抽取、来源定位、去重、冲突识别和项目结构化状态形成。Evidence Store 是外部数据与生成模型之间的可信边界。

### 生成与验证层

基于结构化状态和证据生成报告，再分别验证引用有效性、结论支持度、结构完整性和任务要求。

### Memory 层

分别管理本次运行上下文、跨周期项目状态和历史执行经验。Memory 读取与写入必须经过项目隔离、时效和来源验证。

### 基础设施层

负责数据库、对象存储、队列、锁、指标、日志、告警和密钥管理。第一阶段可使用单进程和文件存储，但模块边界不得依赖这一实现假设。

## 目标执行流程

```text
创建任务
→ 建立 Mission Contract
→ 加载必要项目记忆
→ 生成并校验计划
→ 执行受控工具步骤
→ 标准化来源并抽取 Evidence
→ 形成 Project Snapshot 与 Claims
→ 生成交付物
→ 执行 Citation / Support / Schema 验证
→ 按错误类型定向修订
→ 持久化结果与合格记忆
→ 输出 Artifacts、Trace 和评测数据
```

## 当前实现与目标架构的差距

当前已经由经过校验的确定性 Plan 驱动扫描、抽取、Claim 构建、Artifact 渲染、引用与 Claim 契约验证及有限修订闭环，但仍缺少：

- 根据目标动态生成计划的受限 LLM Planner；
- 标准化跨来源 Locator；
- Analytical Judgement 的语义支持验证；
- 持久化分层 Memory；
- 企业文档和表格连接器；
- 评测执行器与指标；
- Tool Handler 的统一调用协议和参数 Schema；
- Trace 脱敏、持久化与指标聚合；
- 任务恢复、幂等、并发和高可用机制。

这些能力必须按开发计划逐步加入，不能一次性重写整个系统。
