# 记忆系统设计

## 目标

Memory 让 WorkPilot 能够在一次运行中保持上下文、跨周期维护项目状态，并从历史执行经验中改善计划。Memory 不是聊天记录堆积，也不是绕过 Evidence 的事实来源。

## 三层记忆

### 工作记忆

生命周期限定在单次 Run 内，保存：

- 当前 Mission Contract；
- 计划和步骤状态；
- 已读取来源摘要；
- 当前 Evidence 集合；
- 中间 Project Snapshot；
- 验证错误和修订上下文；
- 当前预算消耗。

运行结束后只把经过筛选的内容持久化，避免把全部 Prompt 和临时错误写入长期记忆。

### 项目长期记忆

按项目隔离并跨运行保存：

- 里程碑及状态变化；
- 风险的创建、升级、缓解和关闭；
- 行动项及负责人、截止日期和状态；
- 已确认的决策；
- 来源、证据和 Project Snapshot 版本；
- 历史报告与其验证结果。

长期记忆用于回答“与上周相比发生了什么”，但读取后必须检查来源是否仍有效、状态是否过期。

### 经验记忆

保存可复用但不属于项目事实的执行经验：

- 某类任务的有效计划模板；
- 常见工具失败及安全降级方式；
- Verifier 错误到修订动作的映射；
- 经过评测证明有效的 Prompt 或策略版本。

经验记忆只能影响执行策略，不能作为业务结论的证据。

## 写入门控

写入长期记忆前至少检查：

1. 所属项目和权限范围明确；
2. 来源与 Evidence 可追溯；
3. 对应 Claim 已通过必要验证；
4. 内容没有被标记为临时推测；
5. 记录有效时间、写入时间和版本；
6. 敏感字段经过分类和保护。

## 读取策略

Memory 检索应支持：

- 项目 ID 强过滤；
- 对象类型和时间范围过滤；
- 当前状态优先于历史状态；
- 来源版本和有效期检查；
- 冲突记忆不自动覆盖，而是形成 Conflict；
- 返回记忆时同时返回出处和置信信息。

## 防止记忆污染

- LLM 原始输出默认不能直接进入项目长期记忆；
- 验证失败的 Claim 不得持久化为事实；
- 旧状态不能覆盖更新来源；
- 相同对象更新使用版本或事件，不进行无审计覆盖；
- 删除和纠错必须留下审计记录；
- 经验记忆必须绑定策略版本和评测结果。

## 分阶段实现

1. ✅ 工作记忆接口与 RunContext；
2. 复用高可用 P0 建立的 PostgreSQL Repository，不为 Memory 另建 SQLite 存储；
3. Project Snapshot 版本与跨周期差异；
4. 记忆写入门控和过期策略；
5. 经验记忆与评测联动；
6. 并发控制、缓存和高可用存储。

## 当前状态

当前已经实现 Run 级 WorkingMemory：统一管理步骤状态、EvidenceStore、ProjectSnapshot、验证摘要、修订反馈、Artifact 名称和 Budget Snapshot，并输出不含正文的 `run_context.json`。项目长期记忆和经验记忆尚未实现，因此分层 Memory 整体状态为 🚧。
