# 交接文档：难点、痛点与下一步

## 交接日期

2026-07-21

## 面向读者

接手本项目的工程师。假设你已读过《00-文档阅读指南》《01-项目总体设计》，本文不重复架构介绍，只交接**当前真正的难点、痛点和踩过的坑**，帮你少走弯路。

## 一、这个项目到底在解决什么难题

WorkPilot 的技术难点从来不是"让 LLM 写周报"——那是简单的。真正的难题是**让 LLM 的每条结论都可被机器验证、可追溯到原文**，并且在模型输出不可靠时**宁可失败也不输出未经支持的内容**。

整个系统的复杂度都来自这一条约束。理解这一点，才能理解为什么有 Evidence Candidate 与正式 Evidence 分离、为什么有四个 Verifier、为什么有有界 Repair、为什么 EntityBuilder 默认关闭。它们不是过度设计，而是"可信度"这条主轴逼出来的必要机制。

如果你要改任何东西，先问：**这会不会让一条结论失去原文支撑而系统却判定 passed？** 这是本项目最严重的故障模式（见 BC-001、BC-003）。

## 二、当前最值得注意的痛点（按优先级）

### 痛点 1：Run 状态是内存态，服务重启即丢失历史 🔴

**现象**：`src/workpilot/api/app.py` 的 run 注册表是一个内存 `dict`。虽然产物文件（evidence.json、report 等）已落盘到 `runs_root`，但 `GET /api/runs` 只从内存读，服务一重启历史就空了。

**为什么是痛点**：这直接卡住"生产可用"。它同时阻塞了前端历史列表、并发恢复、检查点续跑等一系列能力。

**建议方向**：先做最轻量的——启动时扫描 `runs_root` 下的目录重建注册表（产物已经在磁盘上，只是没索引）。这比直接上 PostgreSQL 投入小得多，且能立刻解锁前端历史列表。真正的持久化 Repository 是更后面的事。

### 痛点 2：API 无鉴权，只靠 localhost 绑定兜底 🔴

**现象**：`workpilot serve` 默认绑 localhost，工作区和 provider 走白名单，但**没有任何身份认证**。这个服务能触发真实 provider 调用、消耗真实 API 预算。

**为什么是痛点**：任何"让别人也能用"的想法都必须先过这一关。代码注释和 serve 的非本地警告里都写明了，别在没加认证前暴露到公网。

**建议方向**：最小可用是一个 API Token 中间件；要做多用户则需要引入会话与 per-user 预算隔离，工程量陡增，需先做设计记录。

### 痛点 3：长任务在后台线程里跑，没有取消/超时的外部控制 🟡

**现象**：`create_run` 起一个 daemon 线程执行整个 Runtime。真实 provider 一次 Run 可能几十秒到几分钟（见质量基线里 qwen 的 47～169 秒）。目前前端只能轮询，无法取消，线程也没有硬超时。

**为什么是痛点**：Runtime 内部有 Token/步骤/时间预算，但那是"跑起来之后"的软控制；HTTP 层缺少"外部叫停"的手段。一个卡住的真实调用会一直占着线程。

**建议方向**：Runtime 已有预算基础设施，可考虑把 wall-clock 超时提到线程外层，并加一个 `POST /api/runs/{id}/cancel` 配合协作式取消标志。

### 痛点 4：前后端是开发态双进程，未单进程部署 🟡

**现象**：现在要 `workpilot serve`（后端）+ `npm run dev`（前端 vite 代理）两个进程。`web/dist` 能构建，但 FastAPI 没托管它。

**建议方向**：让 FastAPI 用 StaticFiles 挂 `web/dist`，一条 `serve` 命令跑全栈。注意别让静态路由吃掉 `/api/*`。投入小、体验提升明显，适合作为热身任务。

## 三、领域层真正的硬骨头（本项目的智力核心）

这些是比工程痛点更难、也更能体现项目价值的问题。它们已有第一版防线，但远未"解决"。

### 硬骨头 1：证据漂移与结论支持（quote drift）

模型抽取证据时，常把原文"改写"成语义相近但字面不同的 quote，导致行号定位失效、引用无法验证。这是 BC-001、BC-008、BC-012 的共同根源。

当前防线：Candidate 与正式 Evidence 分离、行号视图 Prompt、确定性 Locator Repair（对 exact quote 做唯一匹配还原）、有界 Evidence Repair。相关代码在 `src/workpilot/evidence/`（extraction、quality、store）和 `verification/citation_verifier.py`。

未解决：语义级的"结论是否真被证据支持"（Analytical Judgement）还没有验证器。现在能验证"引用存在且字面匹配"，但不能验证"这条推断性结论在逻辑上成立"。这是下一个大难点。

### 硬骨头 2：结构化实体的字段级证据（EntityBuilder）

把自由文本变成 ActionItem/Risk 这类结构化实体时，每个字段（owner、due date、mitigation…）都要挂上证据。难点是**指标迁移**：改 Prompt 提升了一个字段的召回，往往牺牲另一个（见变更记录里 BC-014 的实测——Mitigation 上去了、Action 和 Due Date 掉了）。

当前状态：EntityBuilder 由 `--entity-projection` 开关控制，**默认关闭**，因为它在真实 Golden 上仍会 failed（BC-015）。主链路用的是更保守的 claim_builder。候选门禁做到了"Action 无损进入、Risk 只能 selected 或登记 duplicate、无依据字段 fail closed"，但精度仍不达标（BC-016、BC-017）。

给接手人的忠告：**不要轻易打开 `--entity-projection` 当默认**。它是实验分支，堆 Prompt 会按下葫芦浮起瓢。要推进请先扩充字段 Golden Case，用数据说话，别凭手感调 Prompt。

### 硬骨头 3：真实模型质量不可复现

所有 100% 的指标都来自 Stub（确定性）或极少数几次 qwen-plus 手动回归。**Stub 全过不代表真实模型质量**。真实模型每次输出都不同，成本和延迟也抖动。Golden Dataset 目前太小，不足以代表真实质量。

给接手人的忠告：看到"100%"先确认是 Stub 还是真实模型。真实基线只有零星几次（见《01-当前实现状态》的"首次真实模型基线"和 BC 记录）。扩充真实 Golden、建立可复现的真实回归，是让指标可信的前提。

## 四、容易踩的坑（血泪经验）

- **产物写入路径**：`create_run` 曾把产物硬编码写到 `workspace_root/_api_runs` 而非 `runs_root`，导致每跑一次测试就往仓库里堆 Run 产物（累积约 290 个文件才被发现）。已修复并加进 .gitignore。改路由时注意 `runs_root` 要贯穿到底。
- **JSON 序列化**：Pydantic `model_dump()` 默认不转 datetime，落盘会炸。用 `model_dump(mode="json")`。EvidenceStore.export() 就踩过（已修）。
- **零检查 = 满分陷阱**：验证器一个检查都没跑时，"错误数 0"会被误判成 100% 通过（BC-003）。加验证逻辑时务必区分"通过"和"根本没检查"。
- **Markdown 双 marker**：Claim 文本自带 `- ` 前缀，渲染时又加一层，导致原文校验失败（BC-004、BC-008）。展示层和校验层对 marker 的处理要一致。
- **Provider 异常泄漏正文**：早期把模型 raw response 塞进异常，导致正文进 Trace/Eval（BC-007）。ProviderResponseError 已移除 raw。加日志时别把模型输出原样带出去。
- **别信 git 里的测试数字**：文档里散落着 160/169/174/191/203 等历次测试数，它们是快照。以实际 `pytest` 结果为准。

## 五、上手路径建议

1. 读《01-项目总体设计》全部 6 篇，建立整体认知；
2. 跑一次：`pip install -e '.[dev,web]'` → `pytest`（应 203 passed）→ `workpilot run --workspace tests/fixtures/workspaces/rich_project --goal 周报 --provider stub --output /tmp/demo`，翻看产物里的 evidence.json 和 verification_report.json，理解可追溯闭环；
3. 起服务看前端：`workpilot serve --workspace-root tests/fixtures/workspaces`（另开）`cd web && npm install && npm run dev`，在报告里点 `[E-xxxx]` 体验"结论跳原文"；
4. 挑一个热身任务落地：**痛点 4（单进程部署）**或**痛点 1 的轻量版（启动扫描 runs_root 重建注册表）**，两者投入小、收益直观；
5. 再啃硬骨头：优先"真实模型可复现回归"（硬骨头 3），因为它是评估其他改动是否真有收益的前提。
