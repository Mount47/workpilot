## 对应代码

- `src/workpilot/domain/models.py`
- `src/workpilot/analysis/claim_builder.py`
- `src/workpilot/analysis/entity_builder.py`

## 要解决的问题

旧链路只有 Claim 的整体文本和 Evidence 引用。风险与行动项 JSON 虽然存在，但 owner、due date、severity 和 mitigation 只能使用占位值，无法进入后续任务系统、风险台账或长期记忆。

本阶段将“报告中的一句话”与“可查询的业务实体”分开：Claim 继续作为最小可验证结论，ActionItem 和 Risk 通过 `claim_id` 关联 Claim，并为重要字段单独保存 Evidence 引用。

## 模型边界

### SupportedText

`SupportedText` 表示可空文本和字段级来源：

- value 为 null 时，Evidence refs 必须为空；
- value 非空时，至少引用一条 Evidence；
- 引用自动去重；
- 只负责结构约束，文本是否真的存在于 Evidence 由 Verifier 判断。

### ActionItem

当前正式字段包括稳定 ID、父 Claim、description、owner、due_date_text、可选 ISO due_date、status 与字段 Evidence。

只对原文中的绝对 ISO 日期做确定性标准化。`本周五`、`下周三` 等相对日期保留在 due_date_text，不根据机器当前日期猜测绝对日期。

### Risk

当前正式字段包括 owner、severity、status、mitigation 和字段级 Evidence。severity/status 没有明确来源时必须为 `unknown`，不能使用展示层默认值。

### Milestone

Milestone 只建立了版本化领域形状，尚未接入模型抽取、验证和 Artifact 主链路，因此仍属于未完成功能。

## Claim 生成契约

ActionItemDraft 和 RiskDraft 嵌套在 ClaimDraft 中，复用一次 Analysis 模型调用。模型侧业务字段使用扁平的 value 与 `*_evidence_refs`，通过后再由 ClaimBuilder 组装 SupportedText，避免让模型重复生成深层领域对象。

具体契约：

1. action_item Claim 必须同时返回 action_item Draft；
2. risk/blocker Claim 必须同时返回 risk Draft；
3. 其他 Claim 禁止携带这两种 Draft；
4. owner、due_date_text、mitigation 必须是所引 Evidence 的原文子串；
5. 字段 Evidence 必须属于父 Claim；
6. 缺失字段返回 null，枚举缺失返回 unknown。

模型 Draft 的扁平化不等于领域模型放宽：值与 refs 的配对约束在 Pydantic Draft 阶段执行，精确原文支持仍由 EntityFieldVerifier 执行。

Provider 的结构化解析失败仍由 Provider Schema Retry 处理；生成成功但字段证据不成立时，由 Runtime 的验证—修订循环处理。

模型仅遗漏 Evidence 的一个 Markdown 列表 marker 时，ClaimBuilder 会在唯一完全匹配的前提下还原 Evidence 原文，并记录 `claim_text_repair_count`。该逻辑不会修复任何其他 paraphrase。

进一步回归后，explicit_fact 增加 primary Evidence 语义：单引用自动选择该 Evidence，多引用可以显式返回 `primary_evidence_ref`。正式 Claim text 直接取 primary Evidence quote，不再信任模型重写的事实正文；无法唯一选择时仍保持严格校验。

## 独立实体投影

BC-014 第一阶段真实回归表明，把 Claim 生成和实体字段抽取放在同一结构化响应中不稳定：Prompt 改善 mitigation 后，Action Recall 和 Risk Precision 反而下降。

Runtime 现已在 ClaimBuilder 之后调用 EntityBuilder：

1. ClaimBuilder 形成不可变、可引用的事实集合；
2. EntityBuilder 读取全部 Claim 和 Evidence，返回扁平 Action/Risk 投影；
3. 系统使用已有 Claim text 作为 description，不允许模型重写实体事实；
4. 字段 Evidence 自动与 Claim Evidence 合并为 entity source refs；
5. 未知 Claim/Evidence 引用直接失败；
6. EntityFieldVerifier 继续执行确定性字段支持验证。

EntityBuilder 可以从 blocker、decision 或 context Claim 中发现明确行动要求，因此实体发现不再被 Claim category 锁死。它也被要求对同一业务风险选择一个 canonical risk Claim，避免把风险描述和响应动作重复计为两条风险。

StubProvider 保留原有确定性投影，不额外调用模型。真实 Provider 只有显式传入 `--entity-projection` 才在每次 Claim 构建后增加一次结构化实体调用。BC-015 真实回归失败后，该能力默认关闭，不能视为生产主路径。

## 字段验证

EntityFieldVerifier 执行确定性检查：

- entity 的 claim_id 必须存在；
- description 和 source refs 必须与 Claim 一致；
- entity source refs 必须精确等于 Claim refs 与全部字段 refs 的并集；
- 字段引用的 Evidence 必须存在；
- SupportedText 必须是至少一条所引 Evidence 的精确子串；
- 已知枚举值必须在 Evidence 中有大小写不敏感的精确文本支持；
- null/unknown 不是错误，但以 `entity.field_unknown` 显式进入验证报告。

字段错误属于 error，会触发最多三轮的现有 Claim 与实体重建、Artifact 重渲染和重新验证。当前仍是整份 Snapshot 重建，定向实体修订尚未实现。

## Artifact 与评测

`action_items.json` 和 `risks.json` Schema 升级到 0.3，全部从正式实体确定性渲染，并增加 `field_evidence`。

Eval Report 新增 Entity Field Support Rate，以及 Action/Risk 五项字段 Population Rate。Support Rate 衡量已填字段是否通过证据验证；Population Rate 只衡量系统是否填值。填充率不等于准确率，后续仍需人工 Golden 字段标注来计算 precision 与 recall。
