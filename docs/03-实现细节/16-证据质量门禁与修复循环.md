# 证据质量门禁与修复循环

## 对应代码

- `src/workpilot/evidence/quality.py`
- `src/workpilot/evidence/extraction.py`
- `src/workpilot/verification/source_coverage_verifier.py`
- `src/workpilot/runtime/runner.py`

## 解决的问题

原有 Runtime 只检查最终 Claim 和 Citation 是否有效，无法区分：

- 来源根本没有被处理；
- Provider 明确返回失败；
- Provider 返回了候选，但候选全部被 quote/行号校验丢弃；
- 来源已有合格 Evidence，但最终 Claim 完全遗漏该来源。

这会导致“保留下来的内容都正确，但报告不完整”仍然 passed。

## 第一层：SourceExtractionReport

EvidenceExtractor 现在为每个来源记录不含正文的统计：

```text
source_id
status
candidate_count
accepted_count
discarded_count
locator_repaired_count
discard_reason_counts
provider_error_type
read_error_type
```

报告只包含计数和错误类型，可以进入 Trace，不泄露原始业务内容。

## 确定性 Locator 修复

Candidate 的 exact quote 已存在于来源，但行号范围非法或声明窗口不包含 quote 时：

1. 搜索原文中的所有 exact occurrence；
2. 计算每个 occurrence 的真实起止行；
3. 选择距离模型建议起始行最近的位置；
4. 保留 quote 原文不变；
5. 在 Evidence metadata 记录原始行号和 `locator_repaired=true`。

quote 不在原文时禁止重定位或模糊接受，仍进入 discard。

## 第二层：EvidenceQualityPolicy

生成 Claim 前执行两个确定性门禁。

### Source Coverage Gate

已扫描来源没有对应提取报告、来源无法读取或 Provider 返回显式 error_type 时失败。

### Evidence Acceptance Gate

全局没有正式 Evidence，或者某来源产生了候选但候选全部被校验丢弃时失败。

来源被正常处理但返回零候选时只产生 warning。因为来源可能与 Goal 无关，不能仅凭零候选认定失败。候选丢弃比例达到 50% 时也产生 warning，当前不单独阻断运行。

## 第三层：有界 Evidence Repair

门禁失败时，Runtime 只重新处理 `repair_source_ids`，而不是扫描和提取全部来源：

```text
首次提取
  -> Evidence Quality Gate
  -> failed
  -> 选择问题来源
  -> 加入失败原因计数、原文 marker 和精确行号修复指令
  -> 第二次提取
  -> 再次执行 Gate
```

当前 `MAX_EVIDENCE_EXTRACTION_ATTEMPTS = 2`。第二次仍失败会抛出 `EvidenceQualityError`，后续 Claim 和 Artifact 不再生成。

OpenAI-compatible 与 Claude Evidence Prompt 使用 `N | source line` 视图。系统明确要求 `N |` 只用于计算 locator，不能写入 quote；Markdown 的 `- `、`1. ` 等原文 marker 必须保留。Repair Prompt 会携带 `quote not found` 等系统错误原因计数，但不会携带被丢弃的 quote 或业务正文。

修复 Extractor 使用 EvidenceStore 当前数量作为 ID 起点，防止新 Evidence 覆盖已有 `E-XXXX`。

## 第四层：Evidence 到 Claim 的来源覆盖

`SourceCoverageVerifier` 检查每个拥有正式 Evidence 的来源是否至少有一条 Evidence 被最终 Claim 引用。遗漏来源产生 `source.claim_coverage` error，并进入已有业务修订循环：

```text
Claim 遗漏来源
  -> verification failed
  -> revision feedback
  -> 重建 Claims
  -> 重绘 Artifacts
  -> 重新验证
```

这解决了首次 qwen-plus 运行中“已扫描来源未进入最终结论，但 Run 仍 passed”的直接问题。

## Trace 事件

- `evidence_quality_evaluated`：每轮门禁结果、候选数、接受数和失败规则；
- `evidence_repair_requested`：修复轮次、问题来源数量和触发规则。

Runtime Trace 当前只记录来源数量和规则 ID，避免扩大敏感日志面。

## 测试

覆盖正常来源、候选全部丢弃、无关来源零候选、Provider 显式错误、修复 ID 连续、Claim 来源遗漏，以及 Runtime 第一次无效而第二次恢复的端到端场景。

## 当前限制

- Repair 仍是同一 Provider 上的定向重试，没有更换解析器；
- 零候选来源只告警，尚未通过来源分类判断其业务重要性；
- SourceCoverageVerifier 尚不支持结构化“合理忽略原因”；
- 没有按 Evidence 类型检查 progress、risk、decision、action_item 的覆盖；
- Locator Repair 和门禁指标已进入 Eval Report，真实模型回归仍待执行。

## 下一步

1. 将 Gate 结果写入评测指标；
2. 增加按 Evidence 类型和 Mission Requirement 的覆盖检查；
3. 将错误类型映射为重新提取、换工具、降低置信度或人工确认；
4. 为每轮 Evidence/Claim 保存安全 Diff；
5. 再将 Repair 动作开放给受限 Planner。
