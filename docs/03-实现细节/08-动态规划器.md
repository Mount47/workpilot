## 当前定位

当前完成了 DeterministicPlanner、受限 ConstrainedLLMPlanner 和确定性降级闭环。它属于模型起草、系统收口的受控规划，不是能够任意创建工具和 DAG 的开放式自主规划。

只有 Route Config 包含 `planning` 时，Runtime 才尝试 LLM Planner；否则继续使用原有 DeterministicPlanner。

## PlanDraft 安全边界

模型只生成 step_id、objective、tool、inputs、dependencies、expected_output、success_criteria 和 evidence_required。goal、plan_id、created_by、validated、created_at、status、attempts 和 last_error_type 全部由系统生成，模型无法覆盖。

Planner Prompt 只暴露 Mission Contract 允许的 ToolSpec，并明确要求将用户 Goal 视为不可信任务数据。

## 默认计划

```text
scan_workspace
→ extract_evidence
→ build_claims
→ render_artifacts
→ verify
→ finalize
```

每个 PlanStep 包含目标、工具、输入、依赖、期望输出、成功标准、Evidence 要求、状态、attempt 和最后错误类型。

## Tool Registry

当前注册六个高层 ToolSpec：

- workspace.scan；
- evidence.extract；
- claims.build；
- artifacts.render；
- verification.run；
- artifacts.finalize。

ToolSpec 声明版本、是否允许 reentry、是否要求 Evidence。Registry 同时管理 Input Model 和已绑定 Handler。当前六个 Runtime 工具都通过 Registry.invoke 调用，不再由 PlanExecutor 直接接收任意闭包。

## 统一工具协议

- ToolInput：Pydantic 参数 Schema，默认拒绝额外字段；
- ToolHandler：声明 ToolSpec、Input Model 和 execute；
- CallableToolHandler：把进程内受控回调适配为统一 Handler；
- ToolResult：内部 output 供同一 Run 传递，output_summary 才允许进入 Trace；
- ToolSpec.version：当前核心工具为 1.0。

PlanValidator 在任何 Handler 执行前校验 PlanStep.inputs。Handler 未注册、未绑定、版本不一致、Input Model 不一致或参数非法都会 fail closed。

## PlanValidator

执行前确定性检查：

- Step ID 唯一；
- Tool 已注册；
- Tool 存在于 Mission Contract 白名单；
- 所有依赖存在；
- 依赖图无环；
- evidence_required 与 ToolSpec 一致；
- max_steps 能覆盖 planning 和初始计划。

任何错误都会在业务 Tool 执行前 fail closed。

## RuntimePlanPolicy

通用 PlanValidator 通过后，还要检查当前 Runtime Handler 兼容性：

- 六个必要 Step ID 必须完整且唯一；
- 每个 Step 必须保持系统规定的 Tool 映射；
- Evidence、Claims、Artifact、Verify 和 Finalize 链路不能被删除；
- 依赖只能指向当前固定执行顺序中的更早步骤；
- 必要依赖不能缺失。

这是当前执行器的临时安全边界。统一 Tool Handler 和串行 DAG Scheduler 已经完成，但在动态步骤的输入输出协议和评测覆盖建立前仍不放宽。

## 降级策略

Provider 瞬时错误经过 RetryPolicy 和 Route Failover 后仍失败、响应结构非法、PlanValidator 失败或 RuntimePlanPolicy 失败时，FallbackPlanner 使用 DeterministicPlanner。

authentication、BudgetExceededError 和未知编程错误不会被降级路径掩盖。`planner_decision` Trace 会记录 requested、selected 和不含模型正文的 fallback_reason。

## PlanExecutor

Executor 检查单步骤依赖状态并维护 pending、running、completed、failed 与 attempt，再通过 Registry-bound Handler 执行。SerialDAGScheduler 根据 dependencies 自动选择 ready 步骤，并补充 blocked、skipped、失败传播与死锁检测。只有 ToolSpec 声明 reentrant 的步骤可以被 Runtime 明确重入。

Runtime 使用 StepResultStore 在步骤之间传递 ToolResult.output。初始主链路由 Scheduler 执行到 verify 后暂停；Runtime 完成业务验证或受控修订后，再恢复 Scheduler 执行 finalize。详细实现见《14-DAG调度与结果上下文》。

当前 Revision Loop 只重入：

```text
claims.build
artifacts.render
verification.run
```

workspace.scan、evidence.extract 和 artifacts.finalize 不会因生成验证失败而重复执行。

## 状态和交付物

- WorkingMemory 导出 Plan ID、创建方式、校验状态和安全 Step 摘要；
- `plan.json` 保存成功 Run 的完整最终计划状态；
- Trace 记录创建、验证和每个 PlanStep attempt。
- Trace 记录工具开始、完成、失败、版本、输入字段名、安全输出摘要和耗时，不记录内部 output。
- Trace 记录 Scheduler 的 ready、blocked、paused、deadlocked 和 completed 事件。

## 当前限制

- LLM Planner 仍必须生成当前六个必要步骤，尚不能真正增删工具步骤；
- 缺少 deterministic 与 LLM Planner 的真实模型对比评测；
- 已实现确定性串行拓扑调度，尚未实现受控并行；
- success_criteria 尚未被自动判定；
- 已有显式 skip 状态，尚无自动跳过策略、取消、幂等键和持久化恢复。
