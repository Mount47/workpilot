# 高可用运行实现

## 当前完成度

WorkPilot 已从“API 进程内 Run dict”演进为 Repository 驱动的 Run 生命周期、执行账本、内部检查点恢复和 Run 级并发控制，并具备 PostgreSQL Adapter 与四版显式 migration。Run、PlanStep、ToolCall、Artifact/Checkpoint Metadata、API 请求幂等、版本化 Checkpoint 重建、数据库租约与双 Worker fencing 已通过真实 PostgreSQL 17 验收，但尚不具备启动扫描和自动恢复调度。

## 已建立的保护

- Run 必须先持久化成功，后台线程才会启动；
- Repository 不可用时 fail closed，不产生静默内存分支；
- API 重建后只要使用同一持久化 Repository，即可查询历史状态与 Artifact；
- output_dir 读取前重新校验 `runs_root` 边界；
- 数据库 URL 只从环境/`.env` 读取并以 SecretStr 保存；
- 内存 Repository 必须通过 `--in-memory-runs` 显式启用。
- API 与 Runtime 使用同一 `run_id`，Trace、Memory、ToolCall 和 Artifact 可稳定关联；
- 相同 `Idempotency-Key` 与请求指纹只创建并启动一个 Run；
- PlanStep/ToolCall 状态通过 Repository Observer 持久化，完成/失败事务不会半更新；
- Artifact 先原子替换，再从实际文件计算摘要并登记 Metadata。
- 六个受限工具使用显式版本化 JSON Codec，未知工具、未知版本和任意 Python 对象 fail closed；
- Checkpoint 文件在 Run 目录内 flush/fsync、原子 replace 并读回校验，数据库只保存相对路径、SHA-256、大小和 Schema 版本；
- ToolCall、PlanStep、Checkpoint Metadata 与 Run sequence 在同一数据库事务提交；文件成功而数据库失败只留下不可恢复使用的孤立文件；
- 内部 CheckpointRestorer 从数据库最新提交点重建 Plan、StepResultStore、EvidenceStore、ProjectSnapshot、渲染产物、验证结果、预算和 WorkingMemory；
- 六个步骤后的 DB-commit/进程退出模糊窗口、文件损坏和并发 sequence 竞争均有故障注入回归。
- `runs` 行保存 `lease_owner`、`lease_expires_at` 和单调递增的 `execution_attempt`；claim/renew 使用数据库时间和 `SELECT FOR UPDATE`；
- Heartbeat 默认按 30 秒 TTL、10 秒间隔续约，Runtime 在步骤开始、工具返回和 Checkpoint 提交前同步检查所有权；
- 所有执行写入在同一事务中先锁 Run 并校验 owner + attempt + expiry；旧 Worker 不能写 PlanStep、ToolCall、Checkpoint、Artifact Metadata 或终态；
- 租约失效或 Repository 不可用属于 Scheduler fatal error，立即中止 DAG；阻塞中的 Provider SDK 调用无法被线程安全强杀，但返回结果不能提交；
- API Worker 采用 claim → Heartbeat → Runtime → fenced terminal commit 生命周期，owner token 不进入 Trace，仅记录 SHA-256 指纹前缀；
- 真实 PostgreSQL 已验证并发 claim 只有一个赢家、过期后 Worker B 接管、Worker A 写入和终态提交均失败、B 可提交下一 Checkpoint 与终态。

## 尚未完成

- Provider 调用去重和 Project/Tenant 级并发配额；
- running Run 的 orphan/recovering 状态与 crash recovery；
- 启动扫描、公开 API/CLI 恢复入口和自动接管；
- 普通 Artifact 的后台对账、孤立文件清理和保留策略；
- Checkpoint 正文加密、密钥轮换和安全擦除；
- 鉴权、租户隔离、可靠任务队列、取消、背压和优雅关闭；
- PostgreSQL liveness/readiness、连接池和 Repository 指标。

因此当前可以描述为“HA-01、HA-02A/B/C 已验收，具备可持久化、可检查点和防 split-brain 的单 Run 执行基础”，仍不能描述为完整高可用。下一验收重点是 HA-02D：启动恢复扫描、公开 API/CLI 恢复入口、Checkpoint 注入 Runtime、恢复调度和 Provider 调用去重；随后进入 HA-03 身份/租户隔离与 P1 可靠队列和生产运维。
