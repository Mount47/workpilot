# 持久化存储实现

## 当前范围

HA-01 持久化 API Run 的身份与生命周期元数据；HA-02A 在相同边界上增加 PlanStep、ToolCall、Artifact Metadata 和 API 请求幂等执行账本；HA-02B 增加版本化 Checkpoint Metadata、跨介质提交顺序和内部状态重建；HA-02C 增加数据库时间租约、Heartbeat、过期接管和单调 fencing。Evidence/Claim 正文和报告仍由文件 Artifact 承载；自动恢复调度、Budget Ledger 和租户模型尚未接入。

## Repository 边界

`src/workpilot/persistence/` 提供：

- `RunRecord`：不可变 Run 元数据，包含 ID、目标、workspace、provider、output_dir、状态、失败原因、Checkpoint sequence、租约、execution attempt、时间和版本；
- `RunRepository`：除 CRUD 外提供 `claim_run/renew_lease/assert_lease/commit_terminal`；
- `InMemoryRunRepository`：线程安全测试和显式开发回退；
- `SQLAlchemyRunRepository`：每个操作使用独立 Session 和事务的持久化实现；
- `RunAlreadyExistsError`、`RunNotFoundError`、`RepositoryUnavailableError`：不携带数据库 URL 的稳定错误。

API 只依赖 Repository 协议。配置 PostgreSQL 时，服务重建后可以从同一 Repository 查询 Run 历史与 Artifact 路径；数据库失败不会自动切换内存历史。

## 数据模型与迁移

首个 Alembic revision 为 `20260722_0001`，创建 `runs` 表：

- `run_id` 主键；
- `goal`、`workspace`、`provider`、`output_dir`；
- `state`、`failure_reason`；
- `created_at`、`updated_at`；
- `version`，用于记录控制面更新版本；执行写入的权威并发 fence 是 `execution_attempt`。

第二个 revision 为 `20260722_0002`：

- 为 `runs` 增加 `idempotency_key_hash` 和 `request_fingerprint`；原始 Key 不入库；
- 新增 `plan_steps`，保存经过验证的计划定义、安全输入哈希、状态、attempt 和成功规则摘要；
- 新增 `tool_calls`，保存逻辑调用键、工具版本、安全输出摘要、Evidence ID 和错误类型；
- 新增 `artifact_metadata`，保存相对路径、实际文件 SHA-256、字节数、媒体类型和写入版本；
- ToolCall 完成/失败与对应 PlanStep 状态在一个数据库事务内更新。

Runtime 通过 `ExecutionObserver` 输出内容最小化的生命周期事件。Observer 不接收 ToolResult 原始 output 或 Provider 原始响应；数据库只保存输入哈希、允许进入 Trace 的 output_summary 和 Evidence ID。

第三、第四个 revision 分别为 `20260722_0003` 和 `20260722_0004`：前者新增 Checkpoint Metadata 与 Run/Step sequence；后者新增 `lease_owner`、`lease_expires_at`、`execution_attempt` 及 `(state, lease_expires_at)` 扫描索引。所有已 claim Run 的执行写入都在事务内锁定 Run，并以数据库时间校验 owner、attempt 和 expiry。

API 接受 `Idempotency-Key` Header：相同 Key 和相同规范化请求返回已有 Run 且不启动第二个线程；相同 Key 对应不同请求返回 409；未提供 Key 时保持每次创建新 Run 的兼容语义。

部署必须显式设置 `WORKPILOT_DATABASE_URL` 并执行 `alembic upgrade head`。应用不会隐式建表或自动迁移。数据库凭证不得通过 CLI 参数传递。

## Artifact 一致性

`output_dir` 由服务端根据 `runs_root/run_id` 生成。读取报告和 Artifact 时会再次验证持久化路径仍位于 `runs_root` 下。ArtifactWriter 使用同目录临时文件、flush/fsync 和原子 replace，Observer 在替换完成后从磁盘实际字节计算 Metadata。Checkpoint 采用“文件先原子提交并读回校验，数据库后事务提交”的协议：文件成功、数据库失败只产生不可恢复使用的孤立文件；数据库提交后文件缺失或摘要不一致则恢复 fail closed。普通 Artifact 的后台对账和孤立文件清理仍未实现。

## 失败行为

- 创建 Run 元数据失败：返回 HTTP 503，不启动 Runtime；
- 数据库查询失败：返回 HTTP 503，不回退内存；
- 后台执行结束但终态写入失败：保留 Runtime 文件 Artifact，并记录不含数据库异常正文的错误日志；
- 重启前处于 running/recovering 的 Run：租约过期后可由另一个 Worker claim，旧 Worker 无法继续写；当前仍不会自动扫描、重建或重跑。
