# 模型输出与供应商差异

## 主要问题

- 模型返回 Markdown Fence 或额外解释；
- JSON 字段缺失、类型错误或枚举越界；
- “没有证据”和“请求失败”都被表示为空数组；
- 不同 Provider 的 Token、停止原因、错误和结构化能力不同；
- 重试可能产生额外成本或重复结果；
- 模型升级后相同 Prompt 的行为发生变化。

## 当前措施

- Structured Output 使用 Pydantic 校验；
- 去除常见 Markdown Fence；
- 设置 temperature=0；
- 允许有限次数重试；
- StubProvider 提供确定性离线测试。
- Provider 错误转换为稳定枚举；
- RetryPolicy 对瞬时错误执行预算感知的指数退避；
- ModelRoute 显式限制能力、最低档位和故障转移；
- Trace 保存任务与 Prompt/Schema 版本标识，不保存正文。

## 真实运行新增发现

2026-07-15 的 BC-005 qwen-plus 回归确认：结构化输出盲重试连续失败，两次 Claim 调用合计消耗 6450 Token，并且 Raw response 通过异常进入 Trace。现已增加脱敏字段错误反馈并移除 Raw 异常正文，分别登记 BC-006 和 BC-007。

需要将以下事件明确区分：

- transport_retry：网络、超时、限流和服务端瞬时错误；
- structured_output_repair：JSON/Pydantic 错误修复；
- business_revision：Claim/Citation 验证失败后的业务修订；
- evidence_candidate_repair：quote/locator 被拒绝后的证据修复。

## 后续设计要求

- Provider 返回统一 `GenerationResult`；
- 统一错误类型：超时、限流、认证、格式、内容安全、服务端错误；
- 区分成功空结果与调用失败；
- 保存 Provider、模型和 Prompt 版本；
- 定义幂等与重试边界；
- 对关键结构使用 Schema 校验并显式失败；
- 用评测而不是单次示例判断模型效果。
