# BC-009：修订失败丢失验证报告

## 元信息

- 状态：已修复
- 首次发现：2026-07-15
- 主要分类：OBSERVABILITY
- 次要分类：EVALUATION_REGRESSION、ENGINEERING_DEFECT
- 关联模块：Runtime、EvalRunner、ArtifactWriter
- 发现 Run：`qwen-plus-bc005-regression-repair`

## 预期结果

只要 Runtime 已执行过验证，无论后续修订成功或异常，最后一次完整检查都应持久化，以便诊断和评测失败 Run。

## 实际结果

真实回归第一次验证执行 69 项检查并发现 15 个错误。随后 `revise.claims` 结构化失败，finalize 未执行，因此没有 `verification_report.json`。Eval 只能输出 Claim Support、Citation 和 Entity Field Support 为 N/A，掩盖了已经发生的验证事实。

## 根本原因

verification_report 只在正常修订循环结束后写入 execution_context，并由 finalize 保存；异常路径的 finally 只保证 run_context 与 trace。

## 修复

- Runtime 保存最新一轮 VerifyResult；
- 正常 finalize 行为保持不变；
- finally 检测到已有验证且报告不存在时，写入 status=`incomplete` 的完整报告；
- error_count 与 total_checks 使用最后一轮结果；
- run_context 的 artifact_names 同步记录该报告；
- 新增“首轮验证失败、修订 Provider 异常”的端到端测试。

## 回归结果

失败修订测试证明 verification_report 在异常路径存在且包含检查和错误，标记为“已修复”。

## 面试复盘要点

高可观测不是只记录最终成功产物。失败越靠后，已经产生的中间诊断越有价值；关键观测数据需要 finally 级持久化保证，而不能依赖 happy-path finalize。
