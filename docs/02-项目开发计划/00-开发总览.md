# 开发总览

## 开发原则

WorkPilot 采用纵向闭环、渐进演进的方式开发。每个阶段必须同时包含设计、实现、测试、评测或运行证据、实现文档和状态更新。

## 阶段路线

| 阶段 | 目标 | 核心交付 | 状态 |
|---|---|---|---|
| 阶段 0 | 建立可运行证据闭环 | 文件扫描、证据抽取、报告生成、引用验证、有限修订 | ✅ |
| 阶段 1 | 统一领域模型与评测基线 | Source、Evidence、Claim、ProjectSnapshot、Golden Cases、Eval CLI | 🚧 主链路和最小基线已完成，数据集待扩充 |
| 阶段 2 | 完整可观测与预算控制 | Step/Model Trace、Token、延迟、预算硬限制 | ✅ 基础闭环完成，精确成本和统一 tool_call 事件后续补充 |
| 阶段 3 | Working Memory | RunContext、步骤、Evidence、Snapshot、验证与预算状态 | ✅ |
| 阶段 4 | 受控动态规划 | Planner、Plan Executor、工具注册、错误到修订策略 | 🚧 受限 LLM Planner 与降级完成，统一 Handler 和动态 DAG 待实现 |
| 阶段 5 | 项目长期记忆 | 项目状态、写入门控、版本、过期与跨周期差异 | ⬜ |
| 阶段 6 | 企业数据连接器 | Markdown/TXT、Excel/CSV、PDF/Word 标准化接入 | 🚧 |
| 阶段 7 | 持久化与恢复 | Run/Memory 持久化、幂等、检查点恢复 | ⬜ |
| 阶段 8 | 高可用工程交付 | 并发限制、任务队列、CI、容器化、服务指标 | ⬜ |

阶段 0 当前可运行，但还不能视为完整产品级实现。其部分能力会在后续阶段被统一模型和接口逐步替换。

## 开发顺序约束

1. 领域模型先于新连接器；
2. 评测基线先于 Planner 和检索优化；
3. Trace 基础先于复杂动态执行；
4. 工作记忆先于长期记忆；
5. 持久化正确性先于并发和多实例；
6. 新能力先通过追加项目点设计，再进入开发清单。

## 单项功能完成定义

一项功能标记为 ✅ 必须满足：

- 设计边界明确；
- 主执行链路实际使用；
- 输入、输出和失败行为确定；
- 核心路径有自动化测试；
- 运行产物或评测能重复验证；
- 实现细节文档已经同步；
- 没有把未实现的扩展描述为现有能力。

## 当前优先事项

1. 建立 deterministic 与 constrained LLM Planner 对比评测；
2. ✅ 统一 Tool Handler、ToolInput 和 ToolResult；
3. 让 Executor 根据已验证 Plan 做拓扑调度，而不是 Runtime 固定调用六个步骤；
4. 增加 success_criteria 的确定性检查和计划调整原因；
5. 完成阶段 4 后再进入项目长期 Memory。
