## 项目判断

WorkPilot 不是“调用一次模型生成周报”的通用 Demo。它的差异化主轴是：**每条结论必须可追溯到原文证据，并通过确定性机器验证；证据不足时宁可 unknown 或失败，也不输出未经支持的内容。**

围绕这条主轴，项目已经建立 Candidate/Evidence 分离、四类验证器、有界 Repair、EntityBuilder fail closed、三类预算硬控制、受限 Planner、确定性降级、DAG 调度、多 Provider 路由、Trace、Golden Evaluation 和 Bad Case 闭环。这部分是已经完成且应持续保护的“正确性内核”，不是下一阶段重新建设的对象。

当前完成度仍够不上“高可用企业级”。HA-01 与 HA-02A/B/C 已补齐持久化执行账本、版本化检查点和 Run 级租约 fencing；剩余空白集中在恢复入口、安全隔离和生产运行层：

1. Checkpoint 已可内部重建，但没有启动扫描、公开恢复入口和恢复调度；
2. API 请求幂等和 Run fencing 已完成，但 Provider 外部调用仍缺少去重与恢复账本；
3. API 没有身份、租户和预算隔离；
4. 后台 daemon 线程缺少可靠队列、取消、超时、背压和优雅关闭；
5. 缺少容器化、健康检查、服务指标、精确成本和脱敏 Trace 持久化。

若项目在校招后重新启动工程扩展，应按“**恢复闭环 → 安全隔离 → 生产运维 → 能力广度**”推进。当前不再优先扩展模型能力、连接器或运行时基础设施；已有测试、Golden 和 Bad Case 作为收尾回归门禁。

## 架构定位

```text
CLI / HTTP API
        ↓
Agent Runtime（状态机 / 预算 / 恢复）
        ↓
Planner → Executor → Tool Registry
        ↓
Connector → Evidence Extractor / Store
        ↓
Project Analyzer（Claim / Entity）
        ↓
Synthesizer → Verifier → Revision
        ↓
Artifact Store

支撑：Providers · Memory · Trace / Metrics · Evaluation
```

正确性内核主要位于中间链路，下一阶段重点补齐 Runtime、Artifact/Repository、安全边界和生产运维支撑。

## 分阶段路线

| 优先级 | 阶段目标 | 核心交付 | 完成门槛 |
|---|---|---|---|
| P0 | 建立高可用地基 | PostgreSQL Repository、Run/Step 持久化、检查点恢复、幂等、并发控制、鉴权与租户隔离 | 进程终止后可安全恢复；重复请求不重复消耗模型预算；并发 Run 不串数据；越权访问被拒绝 |
| P1 | 具备生产运维能力 | 任务队列、取消/超时/背压、容器化、健康检查、Prometheus 指标、精确成本、脱敏 Trace 持久化、优雅关闭 | 服务可部署、可监控、可限流、可终止；故障和成本可定位；日志不泄露敏感正文 |
| P2 | 扩展能力广度 | 真实模型可复现回归、统一 SourceDocument、企业连接器、长期 Memory、受限重规划 | 每项能力都有权限边界、失败语义、Golden/Fixture 和端到端验收，不破坏正确性内核 |

## P0：高可用地基

### P0-1：PostgreSQL Repository 与持久化 Run 索引

状态：✅ HA-01 纵向切片与 HA-02A～C 所需控制面已完成。轻量扫描 `runs_root` 仍只作为后续数据导入或灾备工具，不能替代正式 Repository。

交付项：

- 定义 Repository 接口，隔离 Runtime/API 与 PostgreSQL 具体实现；
- 建立 Project、Run、Plan、PlanStep、ToolCall、Evidence/Claim 索引、Verification、Artifact Metadata 和 Budget Ledger 的版本化表结构；
- 使用数据库迁移管理 Schema，不依赖启动时隐式建表；
- Run 创建、状态迁移、终态和失败原因持久化，API 历史列表直接查询 Repository；
- 文件 Artifact 继续承载大对象，数据库保存版本、Hash、路径、状态和提交关系；
- 定义数据库事务与文件写入的一致性协议，失败时能够识别 incomplete/orphan Artifact；
- 提供现有 `runs_root` Artifact 的一次性索引导入工具。

验收：服务重启后历史和终态不丢失；数据库与 Artifact 不一致时 fail closed 并可诊断；迁移可前进、回滚或明确声明不可逆。

### P0-2：检查点恢复、幂等与并发控制

高可用不是“失败后整条重跑”。恢复必须知道哪些步骤已提交、哪些外部调用不能重复、哪些产物可以复用。

状态：🚧 Checkpoint Codec/Store/Restorer、API 请求幂等、Run 租约、Heartbeat、过期接管和全执行写入 fencing 已完成；HA-02D 的启动扫描、公开恢复入口、恢复调度和 Provider 调用去重待实现。

交付项：

- 在 PlanStep/ToolCall 边界保存检查点、输入摘要、输出引用、attempt 和提交状态；
- 为 Run 创建、Step 执行和 Tool Call 定义稳定幂等键；
- Provider 调用记录 request fingerprint、调用状态和用量，恢复时不盲目重复烧钱；
- 明确 pending/running/committed/failed/cancelled/recovering 状态及合法迁移；
- 使用数据库锁、乐观版本或租约保证同一 Run/Project 不被多个 Worker 同时执行；
- 定义租约过期、Worker 崩溃、部分 Artifact 写入和恢复后二次失败的处理；
- 增加 kill/restart、重复请求、并发竞争、租约过期和部分提交集成测试。

验收：任意步骤后终止进程都能从最近安全检查点恢复；相同幂等键不会产生第二次外部模型调用；并发执行不会覆盖状态或串用 Evidence。

### P0-3：鉴权、多租户与预算隔离

当前 localhost 与 workspace 白名单只能保护本地开发，不能作为企业安全边界。

交付项：

- 引入明确的 User/Tenant/Project 身份上下文；
- API 鉴权覆盖触发 Run、读取 Artifact、查看源文件、取消和恢复；
- 所有 Repository 查询强制携带 tenant/project 过滤条件；
- Provider 凭证、workspace、Artifact、Trace 和 Memory 按租户隔离；
- 建立 per-user/per-tenant Token、成本、并发和速率预算；
- 管理接口与普通运行接口分权，记录不含敏感正文的审计事件；
- 增加跨租户 ID 猜测、路径穿越、越权取消和预算绕过测试。

验收：任何跨租户访问默认拒绝；预算不能通过并发或重试绕过；鉴权失败不会触发模型调用或泄露资源是否存在。

## P1：生产运维能力

### P1-1：任务队列与外部生命周期控制

- 将 daemon 线程替换为可持久化任务队列；Celery、Arq 或其他实现应通过设计记录比较后选择；
- 支持排队、取消、硬/软超时、限流、背压、重试和死信处理；
- HTTP API 与 Worker 解耦，API 重启不影响已提交任务；
- 取消采用协作式标记与外层强制终止组合，明确取消后的检查点和计费语义；
- Worker 支持优雅关闭，停止接单后完成或安全交还租约。

### P1-2：部署、健康检查与运行指标

- Docker/Compose 一键启动 API、Web、Worker、PostgreSQL 和指标组件；
- FastAPI 托管已构建前端或通过统一网关发布，生产环境不依赖 Vite dev server；
- 提供 liveness、readiness、startup 检查，区分进程存活、数据库可用和 Provider 可用；
- 暴露 QPS、队列深度、Run/Step 延迟、错误率、恢复率、重试率、Token、成本和预算拒绝次数；
- 建立最小告警与容量基线，说明备份、恢复和数据库迁移流程；
- CI 运行 unit、integration、small-eval、类型检查、前端 build 和迁移检查。

### P1-3：精确成本与安全可观测

- 建立版本化模型价格表，按真实 Provider/Model/Usage 计算 estimated/actual cost；
- Trace、Metrics 和 Audit Log 分离，定义保留期和访问权限；
- 对 Prompt、模型正文、Evidence quote、凭证、URL 查询参数和异常消息统一脱敏、截断或 Hash；
- Trace 持久化后仍保持 Run → Step → Tool → Model 的关联；
- 指标只包含低基数标签，禁止把正文、用户 ID 或 Run ID 直接作为 Prometheus label。

验收：能够回答“哪次 Run 为什么失败、恢复了几次、调用了哪些模型、花了多少钱”，同时不能从普通日志还原敏感正文或凭证。

## P2：能力广度

P2 不影响 P0/P1 的高可用主线，按业务和评测收益逐项进入：

1. 真实模型可复现回归：扩充 Golden，多次运行记录模型、Prompt/Schema、Token、成本和质量分布；
2. 企业连接器：统一 SourceDocument/ContentUnit/Locator 后，依次接入 Excel/CSV、PDF/Word、任务系统；
3. 长期 Memory：项目状态、Snapshot Diff、写入门控、过期、纠错、防污染和跨租户隔离；
4. 动态步骤与受限重规划：先标准化错误到修复动作，再逐步开放步骤调整，不允许模型绕过 Tool Registry、预算和权限；
5. Provider 原生高级能力：只有业务需求或评测证明收益时再引入。

## 正确性回归门禁

高可用改造不能降低现有可信度：

- Candidate/Evidence 分离、四类验证器、有界 Repair 和 fail closed 语义保持不变；
- 203 个测试与约 90% 覆盖率是 2026-07-21 macOS 项目环境的历史基线；当前 Windows/PostgreSQL 17 基线为 304 passed，后续以 CI 实际产物为准；
- Stub/Golden/Bad Case 必须进入 CI 或发布门禁；
- 恢复、重试和并发不得绕过预算、验证或修订上限；
- 从检查点恢复后的结果必须保留完整 Evidence、Trace、Verification 和 attempt 审计链；
- 基础设施变更导致正确性指标退化时，优先回退变更，不以增加重试掩盖问题。

## 明确暂缓

- 暂不把轻量 `runs_root` 扫描当作正式持久化方案；
- 暂不优先扩充字段 Prompt 或默认开启实验性 `--entity-projection`；
- 暂不批量增加 Provider、连接器或模型原生工具；
- 暂不开放模型任意增删 PlanStep；
- 暂不在租户隔离和 Repository 完成前实现长期 Memory；
- 暂不直接引入 Kubernetes、微服务拆分或多地域容灾；先完成单集群可恢复、可观测、可隔离闭环。
