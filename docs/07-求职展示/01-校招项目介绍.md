# WorkPilot 校招项目介绍

## 一句话定位

WorkPilot 是一个证据驱动、可验证、具备可靠执行基础的项目分析 Agent：它从项目资料中生成周报、风险和行动项，但只有能追溯到原文并通过确定性验证的结论才能进入最终产物。

对外应称为 **production-oriented prototype**，不要称为“完整企业级高可用平台”。项目已实现可信度内核、持久化执行账本、Checkpoint 和 Run fencing；自动恢复入口、鉴权、多租户、可靠任务队列和生产监控仍是后续方向。

## 30 秒介绍

很多 AI 周报工具是 Prompt 进、文本出，模型说什么就展示什么。WorkPilot 的核心差异是把模型输出当成不可信候选：先提取带来源和行号的 Evidence，再构造 Claim 和项目实体，最后用 Citation、Claim Support、Source Coverage、Entity Field 四类确定性验证器做门禁；缺证据时 fail closed，并且 Repair 次数受预算限制。为了让长任务执行更可靠，我还补了 PostgreSQL 执行账本、版本化 JSON Checkpoint、API 幂等、租约和 fencing，避免重复请求和旧 Worker 覆盖新状态。

## 3 分钟讲解顺序

1. **问题**：模型可以生成流畅周报，但流畅不等于真实；项目结论必须能被复核。
2. **主链路**：`Source → Candidate → Evidence → Claim/Entity → Verifier → Artifact`。
3. **关键约束**：模型只能提交候选，不能越过工具白名单、预算和确定性验证器；修复有次数上限。
4. **工程闭环**：Trace、Golden Evaluation 和 17 个 Bad Case 记录失败原因，并把真实失败转成回归用例。
5. **可靠执行**：Run、Step、ToolCall 和 Artifact/Checkpoint Metadata 持久化；Checkpoint 原子写入并与数据库提交关联；lease 与单调 attempt 阻止旧 Worker 继续写。
6. **诚实边界**：当前是面向校招的可靠原型，不具备完整鉴权、租户隔离、任务队列和生产监控。

## 简历表述

以下表述可以直接裁剪到简历，但不要继续扩大范围：

- 设计并实现证据驱动的项目分析 Agent，将模型输出拆分为 Candidate、Evidence、Claim 和结构化实体，通过四类确定性验证器与有界 Repair 实现“结论可追溯、缺证据 fail closed”。
- 构建受限 Agent Runtime：工具白名单、结构化 Planner、确定性降级、串行 DAG、步骤/时间/Token 三类预算，以及多 Provider 路由、重试和 Failover。
- 基于 PostgreSQL 实现 Run/Step/ToolCall 执行账本、API 幂等、版本化 JSON Checkpoint、lease/heartbeat/fencing，并用迁移、并发竞争和故障注入测试验证关键路径。

测试数量和真实模型指标会变化，简历中如需填写数字，应以[当前实现状态](../06-项目状态/01-当前实现状态.md)和本次提交的测试输出为准。

## 高频追问与回答骨架

### 为什么不用模型自己判断引用是否正确？

因为模型既是生成者又是裁判时，错误会同源相关。WorkPilot 让模型只给候选，quote 是否存在、行号是否匹配、Claim 是否被 Evidence 支持、实体字段是否越权引用，都由确定性代码判断。语义判断仍有边界，所以项目明确区分“可确定验证”和“尚未解决的分析性判断”。

### Repair 会不会变成无限烧 Token？

不会。Repair 受步骤、时间和 Token 预算共同约束，并且业务修订次数有上限。不可修复、预算耗尽或仍缺证据时 Run 失败，而不是通过重试掩盖问题。

### Checkpoint 和普通日志有什么区别？

日志用于观察，Checkpoint 用于恢复，必须包含可重建的版本化状态并经过完整性校验。项目使用显式 JSON Codec，不反序列化任意对象；文件原子写入，Metadata、Step 和 ToolCall 状态与 Run sequence 在事务边界内提交。

### lease 和 fencing 为什么要同时存在？

lease 决定当前谁有执行权，但旧 Worker 可能在暂停后恢复。单调 `execution_attempt` 是 fencing token：每次接管递增，所有写入同时校验 owner、attempt 和 expiry，因此旧 Worker 即使恢复也不能提交状态。

### 为什么现在不继续做自动恢复、鉴权和队列？

这些都是真实的企业级方向，但对校招项目继续横向扩张会稀释核心故事，也增加难以完整验证的表面积。当前选择在可信度内核和可靠执行纵向切片完成后冻结功能，优先保证演示、文档、测试和边界陈述一致。

## 面试风险信号

### Red Flags

- 宣称“完整企业级高可用”，却无法展示鉴权、队列、恢复入口、监控和部署证据；
- 只会背组件名，不能解释 Candidate/Evidence 分离或 lease/fencing 的故障场景；
- 把 Stub 100% 指标解释为真实模型质量；
- 无法说明个人完成的设计、实现、测试和复盘部分；
- 遇到失败只增加 Prompt 或重试，没有确定性门禁和回归用例。

### Green Signals

- 能在白板上画出主数据流，并从任意 Claim 追到 Evidence、来源和验证报告；
- 能用一个 Bad Case 说明工程闭环，而非只展示成功结果；
- 能准确区分请求幂等、步骤幂等、Checkpoint 和 Provider 调用去重；
- 能解释事务、原子文件写入和 fencing 的边界；
- 主动说明未实现项，并给出合理的后续顺序。

## 未来情境题

**场景**：服务在模型返回后、Checkpoint 提交前崩溃，另一个 Worker 接管了 Run。

合格回答应先识别模糊窗口，再检查 Provider 调用账本、ToolCall 提交状态、Checkpoint sequence 和当前 fencing token；不能直接假设“从上一步重跑就安全”。当前项目已经保护 Run 写入和接管，但 Provider 外部调用去重尚未完成，因此只能诚实说明仍存在 at-least-once 调用风险，并把它列为后续 HA-02D 的首要任务。
