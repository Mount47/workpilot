# WorkPilot 五分钟演示与验收

## 演示目标

五分钟内证明三件事：

1. 输入项目资料后，系统能够完成一次确定性离线 Run；
2. 最终结论能沿引用回到原文 Evidence；
3. 验证、Trace 和运行状态是可检查产物，不依赖口头说明。

默认演示使用仓库内 Fixture 和 Stub Provider，不需要网络、数据库或 API Key。它用于验证工程链路，不用于证明真实模型质量。

## 演示前准备

要求 Python 3.11+，在仓库根目录执行：

```bash
python -m pip install -e ".[dev]"
python scripts/demo.py
```

脚本默认创建带 UTC 时间戳的新目录，不覆盖已有输出。成功时必须看到：

```text
DEMO_OK
run_state=passed
evidence_count=...
verification_errors=0
trace_events=...
```

如需指定输出目录，必须使用一个尚不存在的路径：

```bash
python scripts/demo.py --output ./runs/interview-demo-01
```

## 五分钟讲解脚本

### 0:00—0:40：问题与定位

“普通 AI 周报把模型文本直接展示，WorkPilot 把模型输出视为不可信候选。只有能定位到原文并通过确定性验证的结论才会进入最终报告。”

### 0:40—1:30：运行一键 Demo

执行 `python scripts/demo.py`，指出它使用 Stub 是为了离线、稳定、可复现。不要把 Stub 指标解释为真实模型效果。

### 1:30—2:30：查看报告与证据

打开控制台输出的 `weekly_report.md`，选择一个 `[E-xxxx]` 引用；再在同目录的 `evidence.json` 中找到对应 ID，展示 quote、来源文件和行号。

证明路径：

```text
weekly_report.md 的 Claim
        ↓ [E-xxxx]
evidence.json 的 quote / source / locator
        ↓
原始 workspace 文件
```

### 2:30—3:20：查看确定性门禁

打开 `verification_report.json`，确认：

- `status` 为 `passed`；
- `error_count` 为 `0`；
- 存在实际检查项，而不是“零检查等于满分”。

说明 Citation、Claim Support、Source Coverage、Entity Field 四类验证器分别保护引用、结论、来源覆盖和结构化字段。

### 3:20—4:10：查看执行过程

打开 `trace.json` 和 `run_context.json`：

- `trace.json` 展示 Planner、工具、步骤、预算和调度事件；
- `run_context.json` 展示最终 Run 状态和安全摘要；
- Trace 不应记录 API Key 或完整敏感正文。

### 4:10—5:00：可靠执行与边界

口头展示 PostgreSQL 执行账本、Checkpoint、lease/heartbeat/fencing 的实现与测试。明确说明默认离线 Demo 不启动 PostgreSQL，不现场伪造分布式故障；竞态与旧 Worker 隔离由自动化测试验证。

最后主动收口：

“这个项目展示的是可信 AI 应用和可靠执行机制，不是已完成的企业级平台。自动恢复入口、鉴权、多租户、可靠队列和生产监控尚未完成。”

## 可靠性证据命令

无需现场部署多 Worker，可以运行确定性测试：

```bash
python -m pytest tests/test_run_lease.py tests/test_lease_heartbeat.py -q
python -m pytest tests/test_checkpoint_codec.py tests/test_checkpoint_store.py tests/test_checkpoint_restore.py -q
python -m pytest tests/test_demo_script.py -q
```

PostgreSQL 条件测试需要单独配置测试数据库，未配置时会按设计跳过。不要为了现场演示临时使用个人数据库或暴露凭证。

## 失败时的降级顺序

1. **前端不可用**：直接展示 Markdown 和 JSON Artifact；核心证据链不依赖 React。
2. **PostgreSQL 不可用**：运行默认离线 Demo，并说明数据库用于持久化与并发控制，不影响可信度主链路展示。
3. **网络或真实模型不可用**：继续使用 Stub；真实模型历史回归只作为已记录实验，不现场承诺可用性。
4. **输出目录已存在**：换一个新目录，脚本按设计拒绝覆盖。
5. **Demo 失败**：保留错误输出，检查虚拟环境和安装状态；不要改 Artifact 或口头宣布成功。

## 验收清单

### 自动验收

- [ ] `python scripts/demo.py` 返回退出码 0；
- [ ] 控制台出现 `DEMO_OK` 和 `run_state=passed`；
- [ ] `evidence_count > 0`；
- [ ] `verification_errors=0`；
- [ ] 必需 Artifact 全部存在；
- [ ] `weekly_report.md` 至少包含一个 `[E-xxxx]`；
- [ ] `tests/test_demo_script.py` 通过。

必需 Artifact：

- `weekly_report.md`
- `evidence.json`
- `verification_report.json`
- `trace.json`
- `run_context.json`
- `project_snapshot.json`

### 人工验收

- [ ] 能从报告的一条 Claim 找到对应 Evidence 和原文行号；
- [ ] 能解释四类验证器而不是只念名称；
- [ ] 能解释 Checkpoint、幂等、lease 和 fencing 的差别；
- [ ] 能说出至少一个 Bad Case 及其回归措施；
- [ ] 能主动说明未实现的企业级能力；
- [ ] 全程不展示 API Key、数据库凭证或敏感原文。
