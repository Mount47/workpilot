# WorkPilot 文档阅读指南

## 这套文档解决什么问题

本目录是 WorkPilot 的设计、开发和演进依据。文档必须回答四个问题：

1. WorkPilot 要解决什么业务问题，不解决什么问题；
2. 系统由哪些模块组成，每个模块承担什么职责；
3. 当前真实实现到了哪里，下一阶段做什么；
4. 新功能如何经过设计、实现、验证和文档同步后进入主线。

代码与测试是实现状态的最终事实来源。文档与代码不一致时，应先按代码和测试修正文档，再继续开发。

## 推荐阅读顺序

### 第一次了解项目

1. [产品定位与边界](./01-项目总体设计/01-产品定位与边界.md)
2. [总体架构](./01-项目总体设计/02-总体架构.md)
3. [模块职责与依赖](./01-项目总体设计/03-模块职责与依赖.md)
4. [数据与领域模型](./01-项目总体设计/04-数据与领域模型.md)
5. [记忆系统设计](./01-项目总体设计/05-记忆系统设计.md)
6. [当前实现状态](./06-项目状态/01-当前实现状态.md)

### 准备参与开发

1. 阅读 [开发总览](./02-项目开发计划/00-开发总览.md)；
2. 阅读 [下一阶段改进路线图](./02-项目开发计划/09-下一阶段改进路线图.md)，确认当前优先级、依赖和验收门槛；
3. 选择对应类别的开发清单；
4. 阅读 `03-实现细节` 中对应模块的实现文档；
5. 阅读 `04-工程问题` 中与该模块相关的问题；
6. 如果是新增能力，按照 [追加项目点设计方法](./05-追加式设计/01-追加项目点设计方法.md)先建立设计记录；
7. 完成代码、测试和验收后，同步状态与实现文档。

### 排查问题

1. 从 [问题总览](./04-工程问题/00-问题总览.md)定位问题类别；
2. 已真实发生的异常从 [Bad Case 总览](./04-工程问题/Bad%20Case记录/00-BadCase总览.md)查找；
3. 阅读对应问题文档中的原因、保护措施和验证方式；
4. 结合 Trace、验证报告和测试复现；
5. 若问题产生新架构决策，新增追加式设计记录。

## 目录职责

| 目录 | 用途 | 何时更新 |
|---|---|---|
| `01-项目总体设计` | 产品边界、总体架构、领域模型、Memory、安全与高可用设计 | 系统级设计发生变化时 |
| `02-项目开发计划` | 按类别拆分功能、阶段、依赖与验收标准 | 每个功能开始和完成时 |
| `03-实现细节` | 记录模块接口、流程、异常、测试和限制 | 模块实现变化时 |
| `04-工程问题` | 记录已知风险、典型故障和解决方法 | 发现或解决工程问题时 |
| `05-追加式设计` | 约束新增项目点，保存设计模板和决策记录 | 新能力进入开发前 |
| `06-项目状态` | 汇总当前真实完成度、变更和文档维护规则 | 每个开发阶段结束时 |

## 状态标记

- ✅：已实现，并有自动化测试或可重复验证；
- 🚧：已经部分实现，但未达到该项验收标准；
- ⬜：尚未实现；
- ⛔：当前阻塞、明确延期或不在当前范围。

“代码中存在类或配置字段”不等于功能已完成。只有主执行路径实际使用、失败行为明确、测试覆盖关键路径后，才标记为 ✅。

## 空白文档说明

部分未来模块只创建了空白文档，用于固定知识入口，避免实现后文档散落。空白文档不代表已有设计或实现；开始该模块前，应先通过追加式设计流程补齐内容。

## 文档维护底线

- 不在状态文档中填写未经实验得出的指标；
- 不把计划能力描述成已实现能力；
- 不仅记录正常流程，还要记录失败、超时、重试和降级行为；
- 新增公共接口、数据结构或状态迁移时必须同步实现细节；
- 完成状态必须能够追溯到代码、测试或运行产物。
